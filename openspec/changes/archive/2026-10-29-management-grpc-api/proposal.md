# Proposal

## Why

Сейчас конфигурация шлюза меняется только из кода: каналы и ревизии создаются вызовами срезов,
маршруты продуктов регистрируются срезами, OpenAPI-документы загружать некуда. Эксплуатация без
управляющего API невозможна: ADR §15.1 требует операций создания/изменения канала, загрузки и
проверки OpenAPI, публикации, активации и отката ревизий, просмотра состояния, а §5.1 — gRPC с
JSON transcoding как единый контракт для gRPC- и REST-доступа. Спайк динамической маршрутизации
завершён, каталог маршрутов есть, поэтому появилась точка, куда должна попадать активированная
ревизия контракта.

## What Changes

- Появляется собственный Protobuf-контракт управляющего API (`lti.gateway.management.v1`) с
  gRPC-сервисом и HTTP-аннотациями: REST-доступ через gRPC JSON transcoding.
- Управляющие операции закрываются ключом API из переменных окружения: сравнение за постоянное
  время, `401` без деталей, отсутствие настроенного ключа — `503` (fail-closed).
- Доступны операции каналов: список, создание, чтение по имени, изменение черновика, публикация
  ревизии, активация, откат. Срезы `Features/Channels` переиспользуются как есть.
- Доступны операции маршрутов продуктов: регистрация и чтение разрешённых каналов и адресов очередей.
- Появляются версии OpenAPI-контрактов: загрузка документа сохраняет его как черновик версии,
  OpenAPI 3.0 принимается, Swagger 2.0 конвертируется (факт конвертации фиксируется в аудите),
  OpenAPI 3.1 отклоняется.
- Загрузка выполняется fail-closed: документ проверяется на поддерживаемые конструкции, локальность
  `$ref`, отсутствие полей рядом с `$ref`, допустимость `format`; отказ возвращает полный список
  проблем с путями до элементов.
- Публикация версии контракта извлекает операции (метод, шаблон, `operationId`) и отклоняется при
  конфликте шаблонов и повторяющемся `operationId`.
- Активация ревизии контракта регистрирует её маршруты в каталоге входящих маршрутов и снимает
  маршруты предыдущей активной ревизии; опубликованные ревизии неизменяемы.
- Появляются операции чтения опубликованных операций контракта и статуса исходящей операции по
  `message_id`.
- Все управляющие операции (успешные и отклонённые) пишутся в аудит с операцией, объектом и
  результатом.

Исключено из объёма:

- валидация входящих тел по JSON-схеме (`NJsonSchema`) — относится к inbound-контуру;
- публикация `InboundMessage` в Rebus и ответы `202`/`503`;
- настройки отдельной операции (`enabled`, очередь получателя, переопределение лимита частоты);
- состояние канала (`GET /v1/channels/{name}/health`: наличие секрета, срок сертификата);
- персональная идентичность и роли (JWT/IdP) — ключ API один, аудит фиксирует факт операции;
- OpenAPI 3.1, внешние `$ref`, административный интерфейс.

## Capabilities

### New Capabilities

- `management-api`: управляющие операции шлюза по gRPC и REST: аутентификация по ключу API,
  жизненный цикл каналов и ревизий, маршруты продуктов, чтение статуса исходящей операции и аудит
  управляющих действий.
- `contract-registry`: версии OpenAPI-контрактов: загрузка и fail-closed проверка документа,
  публикация ревизии с операциями, активация ревизии с регистрацией входящих маршрутов и
  неизменяемость опубликованных ревизий.

### Modified Capabilities

Нет: требования существующих capability (`gateway-host`, `message-contracts`,
`message-serialization`, `channel-registry`, `outbound-dispatch`, `inbound-routing`) не меняются —
управляющий API использует их срезы и каталог маршрутов как есть.

## Impact

- Новое: `Protos/v1/management_api.proto`, `Features/Management/*` (gRPC-сервисы и маппинг),
  `Infrastructure/Management/*` (аутентификация по ключу, аудит), `Infrastructure/OpenApi/*`
  (чтение и fail-closed проверка документа), `Features/Contracts/*` (версии, публикация, активация).
- Пакеты: `Grpc.AspNetCore` 2.85.0, `Microsoft.AspNetCore.Grpc.JsonTranscoding` 10.0.14,
  `Microsoft.OpenApi` 3.11.0 (точная версия фиксируется проверкой API на первом шаге).
- Модель данных: новые сущности версий контрактов и их операций, миграция EF Core.
- `Program.cs`: `AddGrpc().AddJsonTranscoding()`, `MapGrpcService`, middleware аутентификации,
  регистрация срезов и новых обработчиков.
- Тесты: `Features/Management`, `Features/Contracts`, `Infrastructure/OpenApi` на TUnit;
  интеграционные тесты через существующую `GatewayWebApplicationFactory`.
- Контракт для продуктов (`lti.gateway.messages.v1`) не меняется.
- ADR: §15.2 дополняется итоговым перечнем RPC и REST-маршрутов, §14 — использованной версией
  библиотеки чтения OpenAPI.

## Критерии успеха

1. gRPC-вызов и REST-запрос (transcoding) дают одинаковый результат и одинаково требуют ключ API.
2. Канал проходит полный цикл через API: создание → изменение черновика → публикация → активация →
   откат; невалидная публикация возвращает все проблемы и не меняет активную ревизию.
3. Загрузка OpenAPI 3.0 создаёт черновик версии; Swagger 2.0 конвертируется; 3.1, запрещённые
   конструкции и внешние `$ref` отклоняются со списком проблем.
4. Активация ревизии контракта делает её маршруты обслуживаемыми, а маршруты предыдущей ревизии —
   недоступными (`404`).
5. Все управляющие операции без ключа отклоняются без выполнения, каждая операция попадает в аудит.
6. Сборка без предупреждений, все тесты зелёные, приложение стартует и `/health/live` отвечает `200`.
