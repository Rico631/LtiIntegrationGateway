# Design

## Контекст

ADR §8.9 задаёт последовательность: транзакция «операция `Completed` + журнал `pending`» → `Send` →
`sent`; шаг 5 — фоновый диспетчер читает `pending` по индексу и доставляет повторно. Сейчас шаги 1–4
реализованы, шаг 5 отсутствует. Дополнительно повторный запрос (§8.10) собирает результат из
`OutboundOperations` и теряет тело ответа, `Content-Type`, текст ошибки и `correlation_id`.

## Модель данных

| Сущность | Новое поле | Назначение |
|---|---|---|
| `OutboundOperation` | `CorrelationId` (`string?`, 128) | идентификатор бизнес-процесса первого запроса; нужен для идентичного повтора |
| `OutboundMessageLog` | `DeliveryAddress` (`string`, 256) | адрес `rbs2-return-address`, проверенный при приёме запроса |
| `OutboundMessageLog` | `ErrorMessage` (`string?`, 2048) | безопасное описание ошибки первого результата |
| `OutboundMessageLog` | `ChannelRevisionNumber` (`int?`) | номер активной ревизии канала на момент завершения операции (ADR §11.2); `null`, если отказ произошёл до загрузки ревизии |
| `OutboundMessageLog` | `CreatedAtUnixMs` (`long`) | момент записи в миллисекундах Unix; по нему диспетчер упорядочивает пачку |
| `OutboundMessageLog` | индекс `DeliveryStatus`, `CreatedAtUnixMs` | выборка `pending` в порядке поступления без полного сканирования |

`CreatedAtUnixMs` вводится отдельной колонкой, потому что SQLite не поддерживает `ORDER BY` по
`DateTimeOffset` (ARCHITECTURE §8): сортировка должна выполняться в SQL, а не в памяти, иначе пачка
выбирается произвольно и доставляемые записи голодают за недоставляемыми.

Существующая транзакция записи расширяется: адрес доставки, `correlation_id`, текст ошибки, номер
ревизии канала и `CreatedAtUnixMs` сохраняются вместе с телами и статусом. Миграция —
`AddOutboundResultDispatcher`; данные, записанные до миграции, получают пустой адрес и не могут быть
доставлены диспетчером — это известное ограничение перехода, фиксируется в README.

## Восстановление результата

Единый компонент `StoredOutboundResultFactory` строит `OutboundResult` из операции и записи журнала:

| Поле результата | Источник |
|---|---|
| `message_id`, `product_id`, `channel_name` | операция |
| `outcome` | операция (`HTTP_RESPONSE` / `TRANSPORT_ERROR` / `GATEWAY_REFUSED`) |
| `http_status_code` | операция |
| `content_type` | журнал |
| `response_body` | журнал |
| `error_code` | операция |
| `error_message` | журнал |
| `attempt_count` | операция |
| `correlation_id` | операция |

Фабрика используется и при повторном `OutboundRequest`, и диспетчером, поэтому обе ветки дают
одинаковый результат. Текущий `BuildStoredResult` удаляется. Поле `correlation_id` заполняется всегда
(пустая строка, если значения не было), иначе ProtoJSON первого и повторного результата различались бы.

## Приоритет идемпотентности

Порядок в `ProcessOutboundRequestHandler` подчинён ADR §8.10: состояние операции решает, выполняется
ли внешний вызов, и проверяется до правил канала.

```text
1. Обязательные поля запроса.
2. Поиск операции по message_id.
3. Владение: operation.product_id != request.product_id -> PRODUCT_NOT_ALLOWED.
   Состояние чужой операции и журнал не меняются, сохранённый результат не отдаётся.
4. Продукт, адрес отправителя и адрес доставки по конфигурации ProductRoutes.
5. Операция Completed -> сохранённый результат на адрес из текущего сообщения.
   Канал, метод, путь и авторизация повторно НЕ проверяются, внешний вызов не выполняется.
6. Операция Accepted/InProgress -> второй вызов не запускается.
7. Операции нет -> активная ревизия канала, метод, путь, авторизация, вызов.
```

`RefuseAsync` фиксирует отказ в журнале только для операции, созданной этим же запросом: завершённая
или выполняющаяся операция не переписывается, а сохранённый результат не подменяется свежим отказом.
Отказ формируется только по правилам шагов 2–4 (владение и адреса) либо по правилам канала для нового
запроса.

Публикация отказа не меняет признак доставки чужих записей: `CompleteAsync` возвращает созданную запись
журнала, и статус «отправлено» ставится только ей. Если отказ не создавал записи (ранние проверки,
существующая операция), результат отправляется через `SendAsync` без отметки, поэтому `pending`-запись
владельца остаётся в очереди диспетчера и доставляется ему.

## Диспетчер

```text
OutboundResultDispatcher : BackgroundService
  +-- OutboundDeliveryOptions (Enabled, IntervalSeconds, BatchSize)
  +-- GatewayDbContext (scope на цикл)
  +-- StoredOutboundResultFactory
  +-- IBus (через PublishOutboundResultHandler)

цикл:
  пока не остановлен:
    await DispatchPendingAsync(token)
    await Task.Delay(interval, timeProvider, token)

DispatchPendingAsync:
  записи = журнал
           where delivery_status == pending
             and delivery_address != ''
             and exists операция с тем же message_id
           order by created_at_unix_ms
           take BatchSize
  операции пачки читаются одним запросом и сопоставляются по message_id
  для каждой записи (последовательно, в порядке created_at_unix_ms):
     результат = фабрика(операция, запись)
     Send(DeliveryAddress, результат)
     DeliveryStatus = Sent; SaveChanges
```

Условия выборки и сортировка выполняются в SQL: записи без адреса доставки и без операции не
участвуют в пачке и не занимают её место (иначе доставляемые записи голодают), а порядок задаётся
колонкой `CreatedAtUnixMs`. Защитные ветки «операция не найдена» и «адрес пуст» остаются в коде, но
при корректной выборке не срабатывают.

Свойства:

- цикл последовательный: результат одного продукта доставляется в порядке `CreatedAtUnixMs`;
- отправка и фиксация статуса разделены: сбой `Send` даёт `Warning` «отправка не удалась» и запись
  остаётся `pending`; сбой фиксации после успешного `Send` даёт `Error` «результат отправлен, статус не
  зафиксирован — возможен дубль», сущность перечитывается из БД (`ReloadAsync`) и будет отправлена
  снова. Второй случай не выдаётся за потерю результата;
- `Send` и обновление статуса не объединены транзакцией: падение между ними даёт дубль, но не
  потерю — это и есть «минимум один раз»;
- ошибка чтения/записи БД логируется; следующий цикл повторяет выборку;
- распределённой блокировки нет: при нескольких экземплярах возможны дубли (ADR §12, §20 фиксируют
  провайдер блокировок как открытый вопрос). Требование корректности — идемпотентность потребителя
  по `message_id`;
- `TimeProvider` внедряется для детерминированных тестов паузы.

## Конфигурация

| Ключ | Значение по умолчанию | Смысл |
|---|---|---|
| `Outbound:DeliveryDispatcher:Enabled` | `true` | запуск фоновой службы |
| `Outbound:DeliveryDispatcher:IntervalSeconds` | `15` | пауза между циклами, минимум 1 |
| `Outbound:DeliveryDispatcher:BatchSize` | `50` | записей за цикл, 1..500 |

В `appsettings.json` фиксируются значения по умолчанию; `GatewayWebApplicationFactory` добавляет
`Enabled=false`, чтобы фоновые циклы не влияли на существующие тесты. Тесты диспетчера вызывают
`DispatchPendingAsync` напрямую и не зависят от таймера.

## Ошибки и наблюдаемость

- лог: `messageId`, канал, результат попытки; тела и секреты не логируются;
- успешная повторная доставка — `Information`; неуспешная — `Warning`/`Error` с кодом причины;
- счётчики/метрики не добавляются: наблюдаемость — открытый вопрос ADR §17, §20.

## Тестируемость

- `RecordingBus` (подменяемый `IBus.Advanced.Routing.Send`) фиксирует адреса и сообщения; тесты
  проверяют повторную отправку, перевод в `sent`, отсутствие повторов для `sent`, сохранение `pending`
  при ошибке и продолжение обработки остальных записей;
- пачка с `BatchSize = 2`: две недоставляемые записи (`DeliveryAddress = ''`) старше доставляемой —
  доставляемая уходит в `sent` и не голодает; записи без операции и без адреса не участвуют в выборке
  и остаются `pending`;
- тесты идентичности повтора сравнивают ProtoJSON первого и второго результата, включая тело,
  `Content-Type`, `error_code`, `error_message`, `attempt_count` и `correlation_id`, для исходов
  `HTTP_RESPONSE`, `TRANSPORT_ERROR` и `GATEWAY_REFUSED`;
- тест приоритета идемпотентности: завершённая операция при деактивированном канале отдаёт
  сохранённый результат без повторного HTTP-вызова; чужой `product_id` получает `PRODUCT_NOT_ALLOWED`,
  а состояние операции и журнал не меняются;
- тест конфигурации проверяет, что при `Enabled=false` фоновая служба не запускается и `pending`
  остаётся нетронутым.

## Влияние на контракты

Protobuf-контракты, REST/gRPC и формат `OutboundResult` не меняются. Меняются только таблицы
журнала и операции и поведение повторной доставки.

## Отклонения от ADR

Нет. Многoэкземплярная координация явно исключена из объёма и зафиксирована как открытый вопрос
ADR §12, §20; гарантия доставки остаётся «минимум один раз».
