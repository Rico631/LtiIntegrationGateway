# Design

## Context

См. `proposal.md` (Why). Состояние, влияющее на подход:

- `GatewayDbContext` пуст: ни сущностей, ни миграций; SQLite-файл создаётся только при обращении;
- EF Core Sqlite 10.0.14 уже подключён; глобально установлен `dotnet-ef` 10.0.12;
- тесты используют SQLite `:memory:` с открытым соединением (`TestSupport/SqliteInMemoryDatabase`);
- по ADR §7.6 политика повторов состоит из упорядоченных правил с массивом задержек, по §7.5 в
  хранилище допустимы только тип авторизации и ключ конфигурации, по §8.7 путь проверяется
  структурно;
- управляющий API (gRPC + JSON transcoding) в этот change не входит, поэтому срезы пока
  вызываются из тестов.

## Goals / Non-Goals

**Goals:**

- рабочая модель конфигурации канала в SQLite с миграциями;
- вертикальные срезы, покрывающие жизненный цикл: черновик → публикация → активация → откат;
- проверки конфигурации, которые невозможно обойти публикацией;
- гарантия, что значения секретов не попадают в базу.

**Non-Goals:**

- управляющий API, аутентификация администратора, аудит в управляющем контуре;
- чтение активной ревизии в рантайме и её горячая замена;
- продуктовые маршруты, контракты OpenAPI, исходящие вызовы;
- распределённая блокировка публикации (ADR §12 откладывает провайдер).

## Decisions

### D1. Модель данных: ревизия — агрегат настроек

```text
Channel                 Id, Name (уникально), CreatedAt
ChannelRevision         Id, ChannelId, Number (уникален в канале), Status,
                        BaseUrl, AuthType, ConfigKey, HeaderName, UserName,
                        PerAttemptTimeoutMs, OverallCapMs, RetryPolicyJson, CreatedAt
ChannelAllowedMethod    RevisionId, Method            (строка на метод)
ChannelAllowedPath      RevisionId, Template          (строка на шаблон)
ChannelAuditEntry       Id, ChannelId, RevisionNumber, Operation, OccurredAt, Details
```

`Status`: `Draft` → `Published` → `Active` → `Superseded`. У канала не более одной ревизии в
`Draft` и не более одной в `Active`.

**Почему настройки живут в ревизии, а не в канале:** ADR §15.3 требует неизменяемости
опубликованной конфигурации и возможности отката; если настройки хранить в `Channel`, откат
превращается в копирование полей и теряет историю.

**Почему методы и пути — отдельные строки:** их набор проверяется при каждом исходящем запросе;
строки читаются выборкой, а не разбором JSON.

### D2. Политика повторов — JSON-документ внутри ревизии

`RetryPolicyJson` через value converter в типизированный объект (`RetryPolicy` с массивом
`RetryRule`). Валидация — при публикации, на стороне приложения.

**Почему не отдельная таблица:** правила упорядочены и меняются только вместе с ревизией;
отдельная таблица потребовала бы поддержки порядка и транзакционной согласованности без выгоды.
Цена: SQLite не проверяет содержимое — поэтому валидация обязательна и покрывается тестами.

### D3. Неизменяемость обеспечивается срезами, а не базой

Опубликованная, активная и заменённая ревизия не имеют пути изменения: срезы работают либо с
`Draft`, либо создают новую ревизию. Любая попытка изменить не-черновик возвращает проблему
`revision_not_editable`.

**Почему не триггеры/ограничения:** SQLite-ограничения не выражают «эту строку менять нельзя»,
а триггеры скрыли бы нарушение от кода. Тест на попытку изменения опубликованной ревизии
фиксирует поведение.

### D4. Миграции EF Core, применяемые при старте

Добавляется `Infrastructure/Persistence/Migrations` и design-time фабрика
`GatewayDbContextFactory` (нужна `dotnet ef` без запуска приложения). При старте приложения
выполняется `Database.Migrate()`; в тестах — тот же вызов на in-memory соединении.

**Почему миграции, а не `EnsureCreated`:** `EnsureCreated` не умеет развивать схему, а конфигурация
каналов будет расширяться (продуктовые маршруты, контракты).

**Почему применение при старте:** на этом этапе хранилище — один SQLite-файл и один экземпляр;
для промышленной БД порядок применения миграций пересматривается (ADR §11.1).

### D5. Вертикальные срезы в `Features/Channels`

```text
CreateChannel/CreateChannelHandler          + CreateChannelCommand
UpdateChannelDraft/UpdateChannelDraftHandler
PublishChannelRevision/PublishChannelRevisionHandler
ActivateChannelRevision/ActivateChannelRevisionHandler
RollbackChannelRevision/RollbackChannelRevisionHandler
GetChannel/GetChannelHandler
```

Каждый срез — собственный класс с конструкторной инъекцией `GatewayDbContext`, публикующий метод
`HandleAsync` и результат-объект. Посредник (mediator) не вводится: обработчики вызываются
напрямую из тестов сейчас и из gRPC-адаптеров в следующем change.

**Почему результат-объект, а не исключения:** «конфигурация не прошла проверку» — ожидаемый исход
операции; исключения остаются для настоящих сбоев (БД, отмена).

### D6. Проверка конфигурации — один валидатор на публикацию

`Features/Channels/ChannelConfigurationValidator` возвращает список проблем: базовый URL
(абсолютный `https`, без userinfo), методы (из фиксированного набора `GET`, `HEAD`, `POST`, `PUT`,
`PATCH`, `DELETE`), шаблоны путей (начинается с `/`, без схемы, `//`, `..`, `#`, `?`, CR/LF,
длина ≤ 2048), учётные данные (`ConfigKey` обязателен для `bearer`, `api_key`, `basic`), политика
повторов (правил ≥ 1, задержек 1..5, значения > 0, таймауты > 0, общий предел ≥ таймаута попытки).

**Почему один валидатор:** проверки применяются в одной точке (публикация), разносить их по срезам
значило бы дублировать правила и получить расхождение между «создал» и «опубликовал».

### D7. Аудит изменений пишется в тех же транзакциях

Каждая операция среза добавляет строку в `ChannelAuditEntry` в той же транзакции, что и изменение
конфигурации.

**Почему в этой же транзакции:** аудит без изменения (или изменение без аудита) — искажение
истории; SQLite позволяет одну транзакцию на операцию.

## Risks / Trade-offs

- **[Схема зафиксируется до появления читателей]** → модель строго по ADR §7 и §11.2; всё
  неописанное (продуктовые маршруты, контракты) не добавляется.
- **[Миграции при старте]** → приемлемо для SQLite и одного экземпляра; пересмотр — при выборе
  промышленной БД.
- **[Параллельная публикация двух ревизий]** → сейчас не координируется: распределённая блокировка
  отложена (ADR §12). Проверка «у канала один черновик» снижает окно, но не устраняет гонку; это
  записано в открытые вопросы.
- **[`dotnet-ef` 10.0.12 против EF Core 10.0.14]** → миграция генерируется и применяется в тестах;
  при несовместимости версия инструмента поднимается.
- **[Политика повторов не проверяется базой]** → валидация при публикации и тесты на каждое
  правило.

## Migration Plan

1. Миграция создаёт таблицы с нуля; на существующем SQLite-файле применяется при первом старте.
2. Проверка: `dotnet build`, `dotnet test` (тесты используют `:memory:` и применяют миграции),
   запуск приложения с файловой базой.
3. Откат: revert коммита; удалить файл базы, если он был создан этим change.

## Open Questions

- Нужна ли оптимистическая блокировка публикации (поле версии ревизии) до масштабирования на
  несколько экземпляров — решается вместе с выбором провайдера `DistributedLock` (ADR §20).
