# Proposal

## Why

Ревизия ADR выявила расхождения между требованиями и кодом, которые не входят в открытые вопросы §20:

- результат отказа может уйти на `rbs2-return-address`, не проверенный по allow-list (ADR §8.8);
- сообщение с нарушением обязательных полей контракта не журналируется и не диагностируется (ADR §11.2, §18);
- отсутствие секрета активной конфигурации не диагностируется при старте (ADR §7.5);
- публикация канала не предупреждает об отсутствующем секрете (ADR §15.3);
- квота операции создаёт отдельную партицию лимитера, поэтому бюджет канала умножается (ADR §13, §18);
- для сортировки по времени в журналах продублированы колонки `CreatedAtUnixMs` и `ReceivedAtUnixMs`,
  хотя достаточно хранить `DateTimeOffset` в сортируемом виде.

## What Changes

- `OutboundResult` отправляется только на проверенный адрес результата. Если продукт, отправитель или
  адрес не подтверждены, операция завершается, журнал пишется со статусом `Undeliverable`, результат
  не отправляется.
- `OutboundRequest` с пустыми обязательными полями не журналируется: `OutboundRequestHandler` бросает
  `FailFastException`, и сообщение сразу попадает в `lti.gateway.error` без повторов.
- Обязательные поля management-команд проверяются общим валидатором: отказ возвращается в `problems`
  с `severity = ERROR` и `succeeded = false`. Методы чтения сохраняют текущее поведение (`NotFound`).
- `OperationProblem` получает `severity` (`UNSPECIFIED`, `ERROR`, `WARNING`); поле `warnings` у
  `ContractOperationResponse` удаляется, предупреждения передаются как `OperationProblem` с
  `WARNING`. Публикация канала без секрета даёт предупреждение, но остаётся успешной.
- При старте проверяются все активные ревизии каналов и активные версии контрактов. Отсутствие
  секрета или материала клиентского сертификата завершает запуск ошибкой со списком ключей без
  значений.
- Переопределение квоты на операции удаляется из контракта, сущности и API: квота задаётся версией
  контракта и общими настройками, ключ лимита — канал.
- Колонки `CreatedAtUnixMs` и `ReceivedAtUnixMs` удаляются; `DateTimeOffset` журналов хранится как
  Unix-миллисекунды через EF-конвертер, сортировка идёт по `CreatedAt`/`ReceivedAt`.
- ADR актуализируется: квота только на контракте, поведение при отсутствии секрета, предупреждение
  публикации.

Исключено из объёма:

- открытые вопросы ADR §20: OTel/метрики/readiness, JWT/IdP, OAuth2, DistributedLock, промышленный
  транспорт и БД, OpenAPI 3.1, CI;
- список версий контракта и заполнение `external_message_id`;
- HMAC и дедупликация входящих.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `outbound-dispatch`: доставка только на проверенный адрес, статус `Undeliverable`, error-queue для
  невалидного DTO.
- `management-api`: `severity` проблем, проверка обязательных полей команд, удаление квоты операции.
- `contract-registry`: настройки операции без квоты, предупреждение при публикации.
- `channel-registry`: предупреждение об отсутствующем секрете при публикации ревизии.
- `inbound-routing`: квота только из версии контракта, ключ лимита — канал.
- `gateway-host`: проверка секретов активной конфигурации при старте.

## Impact

- `Features/Outbound` — проверки, отказы, статус доставки, error-queue.
- `Features/Management`, `Features/Contracts`, `Features/Channels` — валидация, severity, удаление квоты.
- `Protos/v1/management_api.proto` — `ProblemSeverity`, удаление `warnings` и полей квоты операции.
- `Infrastructure/Persistence` — `Undeliverable`, конвертер `DateTimeOffset`, миграции.
- `src/LtiIntegrationGateway.Tests`, `README.md`, `ARCHITECTURE.md`, `docs/adr`.

## Assumptions

- Сервис в разработке: контракт можно менять без `reserved` и обратной совместимости.
- При старте проверяются только `Active` ревизии и версии; черновики и опубликованные без активации
  не блокируют запуск.
- Для `none` секрет не требуется; для `client_certificate` проверяется загрузка материала.
- «Проверенный адрес результата» — вычисленный `<product_id>.inbox` из `ProductRoutes`.

## Risks

- Fail-fast при отсутствии секрета не даст запустить шлюз, пока не настроены все активные секреты.
- Удаление полей proto и `warnings` ломает существующих потребителей управляющего API.
- Смена поведения отказа меняет тест, который сейчас ожидает доставку на произвольный адрес.

## Success Criteria

- Отказ никогда не публикуется на непроверенный адрес; журнал содержит `Undeliverable`.
- Невалидный DTO оказывается в `lti.gateway.error`, в журнале сообщений его нет.
- Management-команда с пустым обязательным полем возвращает `problems` с `severity = ERROR` и
  `succeeded = false`.
- Публикация канала без секрета успешна и содержит предупреждение `WARNING`.
- Старт с отсутствующим секретом активной конфигурации завершается ошибкой с именем ключа.
- Квота операции отсутствует в API и БД; лимит канала не умножается по операциям.
- Колонок `CreatedAtUnixMs`/`ReceivedAtUnixMs` нет; выборки упорядочены по `CreatedAt`/`ReceivedAt`.
- `dotnet build`, `dotnet test`, проверка `.proto` проходят.
