# Design

## Контекст

ADR §7.3: маршрут создаётся для каждой операции контракта; значения по умолчанию (очередь, авторизация,
квота) берутся из настроек контракта, настройки операции их переопределяют; отключённая операция не
обслуживается (`404`) и фиксируется в аудите; при публикации новой ревизии настройки переносятся по
`operationId`, методу и шаблону. §15.2 требует управляющий `PATCH` настроек операции.

Сейчас `ContractOperation` хранит только метод, шаблон, `operationId` и схемы тела; настройки живут
исключительно на версии контракта.

## Модель данных

| Поле `ContractOperation` | Тип | Смысл |
|---|---|---|
| `Enabled` | `bool`, default `true` | операция обслуживает вызовы |
| `RecipientQueue` | `string?`, 256 | переопределение очереди получателя; `null` — очередь версии |
| `RateLimitPermit` | `int?` | переопределение квоты; `null` — квота версии |
| `RateLimitWindowSeconds` | `int?` | переопределение окна; `null` — окно версии |

Миграция — `AddContractOperationSettings`. Существующие операции получают `Enabled = true` и пустые
переопределения, поэтому поведение после обновления не меняется.

## Действующие настройки

```text
queue    = operation.RecipientQueue ?? version.RecipientQueue
permit   = operation.RateLimitPermit ?? version.RateLimitPermit ?? Inbound:RateLimit:PermitLimit
window   = operation.RateLimitWindowSeconds ?? version.RateLimitWindowSeconds ?? Inbound:RateLimit:WindowSeconds
auth     = версия контракта (переопределение авторизации на операцию не предусмотрено ADR)
enabled  = operation.Enabled
```

Действующие значения вычисляются один раз при построении набора маршрутов (`ContractRouteSets.Build`)
и попадают в `InboundRouteDefinition`; на каждом запросе база не читается.

## Изменяемость настроек

Документ версии и состав операций неизменяемы (ADR §15.3). Настройки операции — отдельный изменяемый
слой:

| Состояние версии | Изменение настроек | Применение |
|---|---|---|
| `Draft` | недоступно: операции появляются при публикации | — |
| `Published` | разрешено | при активации |
| `Active` | разрешено | немедленно: перерегистрация набора маршрутов |
| `Superseded` | запрещено, проблема `version` | — |

Перерегистрация активной версии: построить новый набор, проверить его валидатором, заменить набор с
тем же `RevisionKey`. При ошибке валидации вернуть проблемы и оставить прежний набор; база не
меняется, если каталог не принял набор.

## Публикация и перенос настроек

```text
1. Извлечь операции документа.
2. Найти предыдущую версию канала: максимальный Version < текущего, статус != Draft.
3. Для каждой операции:
     совпадение = operationId (если задан у обеих) либо (метод, шаблон);
     настройки = настройки совпавшей операции предыдущей версии;
     новая операция -> Enabled = true, переопределения пусты.
4. Проверить очередь получателя версии: пустая — проблема `queue` (ADR §15.2).
5. Проверить каждую включённую операцию: действующая очередь непуста; иначе проблема `queue`.
6. Проверить остальные правила (operationId, конфликты шаблонов).
7. Сохранить операции с настройками и опубликовать версию.
```

Очередь получателя версии обязательна всегда (ADR §15.2), независимо от того, отключены ли операции
и есть ли у операции собственное переопределение. Если все операции отключены, версия публикуется,
но ни одна операция не обслуживает вызовы.

## Отключённая операция

Набор маршрутов содержит и включённые, и отключённые операции: конфликт «метод + шаблон» должен
обнаруживаться независимо от `enabled`. `InboundEndpointDataSource` для отключённой операции строит
endpoint с `InboundDisabledOperationHandler` и теми же метаданными маршрута.

Обработчик:

1. не читает тело и не выполняет аутентификацию;
2. пишет `ManagementAuditEntry` (`Operation = "InboundOperationDisabled"`, `Target = channel:method
   template`, `Result = false`, `Details = фактический путь`), создавая scope через
   `IServiceScopeFactory`;
3. отвечает `404` без тела.

Запись аудита может не удаться (БД недоступна): ответ всё равно `404`, ошибка логируется. Значения
заголовков и тела в аудит не попадают.

## Управляющий API

Контракт `lti.gateway.management.v1` (аддитивные изменения, совместимые с существующими
потребителями):

```text
rpc UpdateContractOperationSettings (UpdateContractOperationSettingsRequest)
    returns (ContractOperationResponse)
    PATCH /v1/channels/{channel_name}/contracts/{version}/operations/{operation_id}
    body: "*"

message ContractOperationInfo {
  ... существующие поля 1..3 ...
  bool enabled = 4;
  string recipient_queue = 5;              // пусто — переопределения нет
  int32 rate_limit_permit = 6;             // 0 — переопределения нет
  int32 rate_limit_window_seconds = 7;     // 0 — переопределения нет
}

message UpdateContractOperationSettingsRequest {
  string channel_name = 1;
  int32 version = 2;
  string operation_id = 3;
  optional bool enabled = 4;               // отсутствует — не менять
  optional string recipient_queue = 5;     // пусто — снять переопределение
  optional int32 rate_limit_permit = 6;    // заданное значение должно быть > 0
  optional int32 rate_limit_window_seconds = 7;
}
```

`optional` (proto3) различает «не передано» и «передано пустое/ноль». Валидация: хотя бы одно поле
задано, иначе проблема `settings`; переданные `rate_limit_permit`/`window` должны быть положительны,
иначе проблема `rate_limit` (снять переопределение квоты через API нельзя — известное ограничение);
неизвестная версия/операция — `404`; `superseded` — проблема `version`; операция без `operationId`
в документе не адресуется (`404`). Все поля комментируются по `AGENTS.md`.

## Ошибки и аудит

- проблемы возвращаются полным списком в `problems`, как в существующих срезах;
- каждое изменение настроек пишется в `ManagementAuditEntries` (`UpdateContractOperationSettings`,
  target `channel:vN:operationId`, результат);
- значения секретов отсутствуют: настройки операции их не содержат.

## Тестируемость

- unit-тесты действующих настроек и переноса при публикации;
- интеграционные тесты управляющего API (чтение/изменение опубликованной и активной версии,
  отменённая версия, черновик без операций);
- тесты маршрутов: отключённая операция `404` + аудит, включение без перезапуска, квота операции
  важнее квоты версии, очередь операции важнее очереди версии;
- тест публикации: без очереди версии → `queue` (в том числе все операции отключены); все отключены
  при заданной очереди → успех без обслуживаемых операций;
- тест переноса настроек в новую версию по `operationId`/методу/шаблону.

## Влияние на контракты

`management_api.proto` расширяется аддитивно: новые поля и RPC. Номера существующих полей не
меняются. Сервер всегда заполняет новые поля, поэтому клиент получает фактические значения; клиент,
подключённый к старой версии сервера, увидит значение proto3 по умолчанию (`enabled = false`), что
является ограничением совместимости старого сервера с новым клиентом.

Ключ партиции ограничения частоты включает канал и действующую квоту (`канал|permit|window`), поэтому
операции одного канала с разными квотами имеют независимые счётчики, а смена квоты начинает новое
окно. Каналы по-прежнему не влияют друг на друга; это принятое следствие политики на endpoint
(ADR §13).

## Отклонения от ADR

- Уточнение: настройки операции изменяемы для активной версии, хотя документ версии неизменяем.
  Основание — прямое требование ADR §7.3 о смене `enabled` без перезапуска; фиксируется в спеках.
- Аудит отключённой операции использует `ManagementAuditEntries`; отдельная таблица не вводится.
