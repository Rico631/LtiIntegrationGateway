# Spec Delta

## MODIFIED Requirements

### Requirement: Авторизация берётся из конфигурации

Значение секрета SHALL браться по ключу конфигурации активной ревизии. Отсутствие значения SHALL
приводить к отказу без вызова. Значения секретов SHALL не попадать в результат, журнал и логи.

#### Scenario: Заголовок авторизации формируется

- **WHEN** канал настроен с типом `bearer` и ключом конфигурации, значение задано
- **THEN** HTTP-запрос содержит заголовок авторизации
- **AND** значение секрета отсутствует в результате и журнале

#### Scenario: Значение секрета отсутствует

- **WHEN** ключ конфигурации задан, но значение в конфигурации отсутствует
- **THEN** результат содержит код `SECRET_NOT_CONFIGURED`
- **AND** HTTP-вызов не выполняется

#### Scenario: Клиентский сертификат предъявляется

- **WHEN** активная ревизия использует тип `client_certificate` и материал сертификата настроен
- **THEN** HTTP-вызов выполняется с предъявлением клиентского сертификата
- **AND** значение материала сертификата и пароля отсутствует в результате, журнале и логах

#### Scenario: Материал сертификата не настроен

- **WHEN** для типа `client_certificate` ключ конфигурации не задан, значение отсутствует или
  материал не удаётся загрузить
- **THEN** результат содержит код `SECRET_NOT_CONFIGURED`
- **AND** HTTP-вызов не выполняется
- **AND** сообщение об ошибке не содержит значения материала и пароля

#### Scenario: Неподдерживаемый тип авторизации

- **WHEN** активная ревизия содержит значение типа авторизации вне набора
  `none`, `bearer`, `api_key`, `basic`, `client_certificate`
- **THEN** результат содержит код `AUTH_TYPE_UNSUPPORTED`
- **AND** HTTP-вызов не выполняется

## ADDED Requirements

### Requirement: Соединения исходящих каналов изолированы по ключу

Шлюз SHALL переиспользовать HTTP-обработчик в пределах ключа «базовый адрес, тип авторизации,
отпечаток клиентского сертификата» и SHALL NOT переиспользовать его между разными ключами. Для
исходящих вызовов SHALL применяться TLS не ниже 1.2, SHALL NOT выполняться автоматические
редиректы, серверный сертификат SHALL проверяться всегда.

#### Scenario: Повторный вызов того же канала

- **WHEN** два последовательных вызова выполняются по одному каналу с тем же сертификатом
- **THEN** оба вызова используют один и тот же обработчик соединений
- **AND** соединение не создаётся заново для каждого вызова

#### Scenario: Разные клиентские сертификаты

- **WHEN** два канала настроены с разными клиентскими сертификатами
- **THEN** их вызовы выполняются разными обработчиками
- **AND** сертификат одного канала не предъявляется при вызове другого

#### Scenario: Смена сертификата в ревизии канала

- **WHEN** активная ревизия канала заменена ревизией с другим клиентским сертификатом
- **THEN** последующий вызов выполняется обработчиком, соответствующем новому сертификату
- **AND** обработчик предыдущей ревизии не используется для новых вызовов

#### Scenario: Редирект не выполняется

- **WHEN** внешняя система отвечает `302` с заголовком `Location`
- **THEN** шлюз не выполняет переход по адресу из `Location`
- **AND** продукт получает фактический статус `302` как результат вызова

#### Scenario: Слабая версия TLS

- **WHEN** внешняя система поддерживает только TLS ниже 1.2
- **THEN** соединение не устанавливается
- **AND** результат содержит `outcome = TRANSPORT_ERROR` с кодом `TLS_FAILED`
