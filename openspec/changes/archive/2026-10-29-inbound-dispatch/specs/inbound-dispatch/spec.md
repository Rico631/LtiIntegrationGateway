# Spec Delta

## Purpose

Приём входящих HTTP-вызовов внешних систем по активным операциям контракта: аутентификация,
проверки запроса, валидация тела по схеме операции, передача `InboundMessage` продукту через Rebus,
ответы внешней системе и журнал входящих сообщений.

## ADDED Requirements

### Requirement: Входящий вызов передаётся продукту через Rebus

Активная операция контракта SHALL принимать HTTP-вызов, формировать сообщение `InboundMessage` и
SHALL передавать его в очередь получателя, заданную настройками ревизии контракта. Сообщение SHALL
содержать назначенный шлюзом `message_id`, имя канала, фактический HTTP-метод, фактический
относительный путь, шаблон маршрута, `operationId` при его наличии, `Content-Type`, исходное тело,
query-параметры с сохранением порядка и времени получения.

#### Scenario: Успешный приём

- **WHEN** внешняя система вызывает активную операцию с валидным телом
- **THEN** шлюз передаёт `InboundMessage` в очередь получателя
- **AND** внешняя система получает `202 Accepted`

#### Scenario: Содержимое сообщения

- **WHEN** запрос `POST /callbacks/contracts/42/status?source=bank` с телом принят
- **THEN** сообщение содержит метод `POST`, путь `/callbacks/contracts/42/status`,
  шаблон `/callbacks/contracts/{id}/status`, `Content-Type`, исходное тело и query-параметр `source=bank`
- **AND** `message_id` назначен шлюзом и не совпадает с идентификатором внешней системы

#### Scenario: Идентификаторы внешней системы

- **WHEN** внешняя система передаёт собственный идентификатор события
- **THEN** он не подменяет `message_id` шлюза
- **AND** сообщение остаётся пригодным для обработки продуктом

### Requirement: Тело запроса проверяется по схеме операции

Шлюз SHALL проверять тело запроса по схеме операции из опубликованной ревизии контракта и SHALL не
передавать продукту запрос, не соответствующий схеме. Неподдерживаемый `Content-Type` SHALL
отклоняться, синтаксически некорректный JSON и превышение глубины JSON SHALL отклоняться как
некорректный запрос.

#### Scenario: Тело соответствует схеме

- **WHEN** тело запроса удовлетворяет схеме операции
- **THEN** запрос принимается и передаётся продукту

#### Scenario: Тело не соответствует схеме

- **WHEN** тело не содержит обязательного поля или имеет неверный тип
- **THEN** ответ имеет статус `422 Unprocessable Content`
- **AND** сообщение продукту не передаётся

#### Scenario: Неподдерживаемый Content-Type

- **WHEN** операция объявляет только `application/json`, а запрос приходит с `text/plain`
- **THEN** ответ имеет статус `415 Unsupported Media Type`

#### Scenario: Синтаксически некорректный JSON

- **WHEN** тело запроса не разбирается как JSON
- **THEN** ответ имеет статус `400 Bad Request`

#### Scenario: Слишком глубокая вложенность

- **WHEN** глубина JSON в теле превышает 64 уровня
- **THEN** ответ имеет статус `400 Bad Request`

### Requirement: Параметры запроса ограничены по количеству

Шлюз SHALL отклонять запрос, если количество query-параметров превышает 64.

#### Scenario: Превышение количества параметров

- **WHEN** запрос содержит 65 query-параметров
- **THEN** ответ имеет статус `400 Bad Request`
- **AND** сообщение продукту не передаётся

### Requirement: Входящий вызов аутентифицируется по настройкам ревизии

Тип аутентификации SHALL браться из настроек ревизии контракта: `none`, `api_key`, `basic` или
`client_certificate`. Секрет SHALL браться из конфигурации по ключу и сравниваться за постоянное
время. Отказ SHALL возвращать `401` без деталей; отсутствие настроенного секрета SHALL возвращать
`503`.

#### Scenario: Ключ API

- **WHEN** ревизия настроена с типом `api_key`, имя заголовка задано, значение настроено
- **THEN** вызов с корректным заголовком принимается
- **AND** вызов без заголовка или с неверным значением получает `401`

#### Scenario: Basic

- **WHEN** ревизия настроена с типом `basic`, имя пользователя задано, пароль настроен
- **THEN** вызов с корректными учётными данными принимается
- **AND** вызов с неверным паролем получает `401`

#### Scenario: Клиентский сертификат

- **WHEN** ревизия настроена с типом `client_certificate` и хостинг предъявил валидный клиентский сертификат
- **THEN** вызов принимается
- **AND** вызов без клиентского сертификата получает `401`

#### Scenario: Секрет не настроен

- **WHEN** для типа `api_key` или `basic` значение секрета отсутствует в конфигурации
- **THEN** ответ имеет статус `503 Service Unavailable`
- **AND** сообщение продукту не передаётся

#### Scenario: Отказ без раскрытия причины

- **WHEN** аутентификация не пройдена
- **THEN** тело ответа не содержит причины отказа и ожидаемого значения
- **AND** значение секрета не попадает в журнал и логи

### Requirement: Ответ внешней системе отражает факт передачи

Шлюз SHALL отвечать `202 Accepted` только после успешной передачи сообщения в Rebus. Если передача
не удалась, ответ SHALL быть `503 Service Unavailable`; `200 OK` для входящих вызовов не
используется.

#### Scenario: Передача не удалась

- **WHEN** передача сообщения в очередь получателя завершилась ошибкой
- **THEN** ответ имеет статус `503 Service Unavailable`
- **AND** успешный приём не подтверждается

#### Scenario: Отсутствие 200

- **WHEN** запрос принят и передан продукту
- **THEN** ответ имеет статус `202`, а не `200`

### Requirement: Входящие вызовы фиксируются в журнале

Каждый принятый и каждый отклонённый по проверкам вызов SHALL фиксироваться в журнале
`InboundMessageLog` с телом запроса, методом, фактическим путём, шаблоном маршрута, `operationId`,
query-параметрами, статусом передачи, кодом ошибки, ревизией конфигурации и временем получения.
Авторизационные заголовки и значения секретов в журнал SHALL не попадать.

#### Scenario: Принятый вызов

- **WHEN** вызов передан продукту
- **THEN** журнал содержит запись со статусом передачи «отправлено»
- **AND** запись содержит тело запроса и ревизию конфигурации

#### Scenario: Отклонённый вызов

- **WHEN** вызов отклонён схемой, аутентификацией или сбоем передачи
- **THEN** журнал содержит запись с соответствующим статусом и кодом ошибки

#### Scenario: Секреты отсутствуют в журнале

- **WHEN** вызов принят с типом аутентификации `api_key` или `basic`
- **THEN** в журнале нет значения ключа, пароля и заголовка авторизации

### Requirement: Дедупликация входящих вызовов не выполняется

Шлюз SHALL не дедуплицировать входящие события: каждый вызов внешней системы SHALL становиться
отдельным сообщением продукту, даже если тело и путь совпадают с предыдущим вызовом.

#### Scenario: Повторный одинаковый вызов

- **WHEN** внешняя система дважды отправляет один и тот же запрос
- **THEN** продукт получает два сообщения с разными `message_id`
- **AND** оба вызова отражены в журнале
