# Proposal

## Why

Динамические входящие маршруты реализованы только как спайк: любая активированная операция
отвечает диагностическим JSON и ничего не передаёт продукту. Входящий контур из ADR §9 (приём
запроса внешней системы, аутентификация, валидация по схеме, публикация `InboundMessage`, ответы
`202`/`503`, журнал) не реализован, поэтому шлюз пока не может принимать реальные вызовы банков.
Кроме того, у версии контракта нет настроек (очереди получателя, авторизации, лимита частоты), без
которых публикация `InboundMessage` невозможна, а в операциях не сохраняются схемы тела — валидировать
запрос нечем.

## What Changes

- Появляется приём входящего вызова вместо диагностического ответа: запрос проходит аутентификацию,
  проверки запроса, валидацию тела по схеме операции и передаётся продукту сообщением
  `InboundMessage` через Rebus.
- Аутентификация входящего вызова задаётся настройками ревизии контракта: `none`, `api_key`, `basic`,
  `client_certificate` (mTLS проверяется хостингом, приложение доверяет валидному сертификату).
  Секреты берутся из окружения по ключу конфигурации и в базу не попадают.
- Ответы внешней системе: `202` после успешного `Send`, `503` при неудаче передачи, `400` для
  синтаксически некорректного запроса и слишком глубокого JSON, `401` без деталей при отказе
  аутентификации, `404` для неизвестного маршрута, `405` для недопустимого метода, `415` для
  неподдерживаемого `Content-Type`, `422` при несоответствии схеме, `429` при превышении квоты,
  `503` при отсутствии настроенного секрета.
- При публикации версии контракта из документа извлекаются схемы тела по каждому `Content-Type` с
  развёрнутыми локальными `$ref`; публикация без очереди получателя отклоняется.
- У версии контракта появляются настройки: очередь получателя, тип авторизации и её параметры, лимит
  частоты. Настройки изменяются только в состоянии черновика и доступны через управляющий API.
- Маршрут входящего вызова несёт настройки своей ревизии, поэтому лимит частоты и аутентификация
  применяются без обращения к базе на каждом запросе.
- Каждый принятый и отклонённый вызов фиксируется в журнале `InboundMessageLog` с телом запроса,
  маршрутом, операцией, статусом передачи и ревизией конфигурации; секреты в журнал не попадают.
- Дедупликация входящих событий не выполняется (ADR §10.3): повторный вызов от внешней системы —
  отдельное событие для продукта.

Исключено из объёма:

- настройки отдельной операции (`enabled`, переопределение очереди и лимита) — публикация отклоняется,
  если очередь не задана на версии контракта; отключение операции появится вместе с этими настройками;
- подпись HMAC-SHA256 и дополнительная верификация тела;
- заполнение `external_message_id` и `correlation_id` во входящем сообщении — источников этих
  значений у шлюза нет, поле остаётся незаполненным;
- очистка журнала и политика хранения (ADR §11.2 — бессрочно);
- ограничение размера тела в приложении — остаётся на ingress (ADR §13).

## Capabilities

### New Capabilities

- `inbound-dispatch`: приём входящего HTTP-вызова по активному маршруту: аутентификация, проверки
  запроса, валидация тела по схеме операции, сборка `InboundMessage`, публикация в Rebus, ответы
  внешней системе и журнал входящих сообщений.

### Modified Capabilities

- `inbound-routing`: маршрут передаёт запрос в приём входящего вызова (диагностический ответ
  спайка удаляется), лимит частоты берётся из настроек ревизии контракта.
- `contract-registry`: публикация сохраняет схемы тела операций и отклоняется без очереди
  получателя; добавляются настройки версии контракта.
- `management-api`: настройки версии контракта доступны для чтения и изменения через управляющий API.

## Impact

- Новое: `Features/Inbound` (приём вызова, аутентификация, валидация, публикация, журнал),
  сущность `InboundMessageLog`, пакет `NJsonSchema` для валидации тела.
- Изменяется: `ContractVersion`/`ContractOperation` (настройки и схемы), `InboundRouteDefinition`
  и метаданные endpoint'а, `ContractRouteSets`, срезы публикации и активации контракта,
  `ManagementApiService.Contracts`, `Program.cs` (регистрация приёма и лимита), миграция.
- `.proto` управляющего API расширяется настройками версии контракта; контракт сообщений
  `lti.gateway.messages.v1` не меняется — `InboundMessage` уже объявлен.
- Тесты: приём вызова, аутентификация, коды ответов, журнал, лимит из контракта, извлечение схем.
- ADR: §9 и §15.2 дополняются фактическим поведением (реализовано); отклонения фиксируются в отчёте.

## Критерии успеха

1. Активированная операция принимает валидный запрос, передаёт `InboundMessage` в очередь получателя
   и отвечает `202`; тело, метод, путь, шаблон и `operationId` доходят до продукта без искажений.
2. Невалидный по схеме запрос отвечает `422` и не публикуется; неизвестный маршрут — `404`;
   недопустимый `Content-Type` — `415`; слишком глубокий JSON — `400`.
3. Все четыре типа аутентификации работают по настройкам ревизии; отказ — `401` без деталей,
   отсутствие секрета — `503`.
4. При сбое передачи в Rebus ответ — `503`, факт фиксируется в журнале.
5. Публикация контракта без очереди получателя отклоняется; схемы тела доступны для валидации.
6. Сборка без предупреждений, все тесты зелёные, существующие сценарии остаются рабочими.
