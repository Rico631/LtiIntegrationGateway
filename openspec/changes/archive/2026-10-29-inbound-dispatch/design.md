# Design

## Context

См. `proposal.md` — Why. Существенное для реализации:

- `Infrastructure/Routing` уже публикует динамические endpoint'ы из каталога, но обработчик —
  `InboundProbeHandler`, отвечающий диагностическим JSON; метаданные endpoint'а содержат только канал.
- `ContractVersion`/`ContractOperation` хранят документ, номер, состояние, метод, шаблон и
  `operationId`; настроек и схем тела нет, поэтому приём вызова невозможен.
- `PublishContractVersionHandler` извлекает операции через `OpenApiDocumentValidator.ExtractOperations`
  и проверяет конфликты через `InboundRouteSetValidator`.
- `ActivateContractVersionHandler` строит `InboundRouteSet` и активирует его в `InboundRouteCatalog`.
- Секреты доступны через `ISecretStore`, значения в базе не хранятся.
- ADR §9.2 задаёт порядок обработки, §9.5 — коды ответов, §13 — требования к аутентификации,
  §14 — валидация тела через `NJsonSchema` за абстракцией, §10.3 — отсутствие дедупликации.

## Goals / Non-Goals

Цели дизайна:

- приём вызова встраивается в существующий конвейер динамических маршрутов без переписывания каталога;
- все данные, нужные на запросе, лежат в метаданных endpoint'а — база на пути запроса не читается;
- схемы тела компилируются один раз на активированную ревизию, а не на каждый запрос.

Вне дизайна:

- настройки отдельной операции и признак `enabled` (публикация требует очередь на версии контракта);
- HMAC, дедупликация, очистка журнала, ограничение размера тела (ingress).

## Decisions

### D1. Извлечение схем тела при публикации

`OpenApiDocumentValidator` дополняется извлечением `requestBody.content`:

```text
для каждого content-type в requestBody.content:
    schema = inline-refs(schema, root, depth: 0)
inline-refs(node, root, depth):
    $ref #/... -> подставить целевой узел и рекурсивно обработать
    глубина > 32 или повтор узла -> проблема публикации "schema: циклическая ссылка"
```

Результат сохраняется в `ContractOperation.RequestSchemas` как JSON-объект
`{ "application/json": { ... }, ... }`. Инлайнинг выполняется по исходному `JsonNode`, а не моделью
`Microsoft.OpenApi`: локальные `$ref` уже проверены на допустимость (ADR §14), а нормализованная
модель теряет часть структуры.

**Почему инлайнинг, а не разрешение ссылок при валидации:** сохранённая схема становится
самодостаточной, её можно скомпилировать один раз и не хранить документ в памяти на каждом запросе.

### D2. Схемы компилируются один раз на ревизию

`InboundSchemaCache` (singleton) хранит `ConcurrentDictionary<Guid, OperationSchemaSet>`, где ключ —
`ContractVersionId`, а значение — отображение `(метод, шаблон)` → `JsonSchema` (`NJsonSchema`) и
набор допустимых `Content-Type`. Заполняется при активации версии, удаляется при её деактивации.

**Почему не компилировать на запросе:** ADR §14 требует однократную сборку; компиляция на каждый
вызов добавила бы задержку и нагрузку на CPU.

**Проверено (задача 1.1):** `NJsonSchema` **11.6.1** компилирует схему через
`await JsonSchema.FromJsonAsync(string)` и валидирует документ синхронно: `schema.Validate(json)`
возвращает коллекцию `ValidationError` (пустая — документ валиден). Требования `required` и
`additionalProperties: false` работают как ожидается; пробный тест — `SchemaValidationProbeTests`.

### D3. Маршрут несёт все настройки ревизии

`InboundRouteDefinition` расширяется:

```text
ChannelName, HttpMethod, Template,
ContractVersionId, OperationId,
RecipientQueue, AuthType, ConfigKey, HeaderName, UserName,
RateLimitPermit, RateLimitWindowSeconds
```

`InboundEndpointDataSource` добавляет метаданные `InboundRouteMetadata` (канал остаётся в метаданных
для партиции лимита) и передаёт `RequestDelegate` приёма. База на пути запроса не читается.

### D4. Конвейер приёма вызова

`InboundRequestHandler` (singleton, `RequestDelegate`) выполняет шаги в фиксированном порядке:

```text
1. query-параметры > 64                         -> 400
2. Content-Type не входит в схемы операции      -> 415
3. тело непустое, а схема не объявлена          -> 400
4. аутентификация по настройкам маршрута        -> 401 / 503
5. разбор тела: JsonDocumentOptions.MaxDepth=64 -> 400
6. валидация по схеме (NJsonSchema)             -> 422
7. сборка InboundMessage, журнал pending
8. bus.Send(recipientQueue, message)            -> ошибка: журнал failed, ответ 503
9. журнал sent, ответ 202
```

Порядок выбран так, чтобы дорогие операции (чтение секрета, разбор, валидация) не выполнялись для
заведомо некорректного запроса, а сообщение продукту не уходило до полной проверки.

**Почему `202` только после `Send`:** ADR §9.5 — ложное подтверждение приёма недопустимо.

**Реализовано (задачи 8.1–8.4):** шаги 1–9 выполнены; дополнительно:

- тело читается один раз в память до проверок, поэтому запись журнала отклонённого вызова содержит
  исходное тело без повторного чтения потока;
- валидация по схеме выполняется только для JSON-типов содержимого (`application/json` и `*+json`):
  для остальных объявленных типов тело передаётся как есть, что соответствует §9.3 (формат задаётся
  `content_type`);
- передача идёт через `IInboundMessagePublisher` (реализация `RebusInboundMessagePublisher`), поэтому
  сбой транспорта воспроизводится в тестах без подмены `IBus`;
- запись журнала выполняется в отдельном DI-scope (`InboundMessageLogWriter`), сбой журнала даёт `503`
  и не подтверждает приём.

**Проверено (задача 1.2):** `JsonDocument.Parse(json, new JsonDocumentOptions { MaxDepth = 64 })`
бросает `JsonException` на документе глубже 64 уровней, поэтому проверка глубины выполняется разбором
тела до валидации по схеме и даёт `400` без дополнительного кода.

### D5. Аутентификация входящих вызовов

`InboundRequestAuthenticator` — класс без состояния, вызывается из конвейера:

| Тип | Проверка |
|---|---|
| `none` | пропуск |
| `api_key` | значение заголовка (имя из настроек) сравнивается с секретом за постоянное время |
| `basic` | `Authorization: Basic`, пользователь из настроек, пароль из секрета, сравнение за постоянное время |
| `client_certificate` | наличие клиентского сертификата в `HttpContext.Connection.ClientCertificate`; валидность проверена хостингом |

Отсутствие настроенного секрета для `api_key`/`basic` — `503`; отказ — `401` без тела. Детали отказа
пишутся в лог на уровне Warning без значения секрета.

**Почему mTLS проверяется по наличию сертификата:** ADR §7.3 и §13 относят валидацию цепочки к
хостингу (Kestrel/ingress); приложение не может и не должно повторять проверку цепочки.

### D6. Журнал входящих вызовов

`InboundMessageLog` (новая сущность): `MessageId`, `ChannelName`, `ContractVersionId`, `HttpMethod`,
`RelativePath`, `RouteTemplate`, `OperationId`, `ContentType`, `RequestBody`, `QueryParameters` (JSON),
`DeliveryStatus` (`pending`/`sent`/`failed`), `ErrorCode`, `ReceivedAt`.

Запись создаётся до `Send` со статусом `pending`, затем обновляется на `sent` или `failed`. Если
обновление не удалось, ответ уже определён фактом `Send`; ошибка записи логируется.

**Почему не после `Send`:** запись до отправки гарантирует, что факт приёма не потеряется при сбое
после отправки.

### D7. Лимит частоты из настроек ревизии

Политика `inbound-per-channel` получает значения из метаданных endpoint'а
(`RateLimitPermit`, `RateLimitWindowSeconds`) с откатом на `InboundRateLimitOptions`. Ключ партиции —
`channel|permit|window`: `FixedWindowRateLimiterOptions` фиксируются при создании партиции, поэтому
разные лимиты разных ревизий одного канала не должны попадать в одну партицию.

### D8. Настройки версии контракта и управляющий API

`ContractVersion` получает `RecipientQueue`, `AuthType`, `ConfigKey`, `HeaderName`, `UserName`,
`RateLimitPermit`, `RateLimitWindowSeconds`. Управляющий API дополняется RPC:

```text
GetContractVersion            GET   /v1/channels/{channel_name}/contracts/{version}
UpdateContractVersionSettings PATCH /v1/channels/{channel_name}/contracts/{version}/settings
```

Изменение допускается только для `Draft`; иначе проблема `version`. Тип авторизации проверяется по
набору из ADR §7.3, иначе проблема `auth_type`. Очередь обязательна при публикации, а не при
сохранении черновика — черновик можно готовить постепенно.

### D9. Публикация: операции, схемы и очередь

`PublishContractVersionHandler` дополнительно:

1. извлекает схемы тела (D1) и сохраняет их в операциях;
2. отклоняет публикацию, если `RecipientQueue` пуста (`queue: очередь получателя обязательна`);
3. сохраняет операции с настройками по умолчанию из версии (настройки операции — вне объёма).

### D10. Активация: маршруты и кэш схем

`ActivateContractVersionHandler` строит `InboundRouteSet` из операций, включая настройки версии,
активирует набор в каталоге (порядок из предыдущего изменения сохраняется), затем заполняет
`InboundSchemaCache` для новой версии и очищает кэш предыдущей.

### D11. Тесты

- Аутентификация: юнит-тесты `InboundRequestAuthenticator` на `DefaultHttpContext` с поддельным
  `ITlsConnectionFeature` для mTLS (TestServer не выполняет TLS-рукопожатие).
- Сквозные тесты: `GatewayWebApplicationFactory` + `InboundFixture` (канал, контракт, настройки,
  активация) и in-memory endpoint Rebus с коллектором `InboundMessage`.
- Коды ответов: 202, 400 (глубина JSON, количество параметров, битый JSON), 401, 404, 405, 415, 422,
  429, 503 (нет секрета и сбой `Send`).
- Журнал: записи для принятого и отклонённого вызова, отсутствие значений секретов.

## Risks / Trade-offs

- **[API `NJsonSchema` проверяется по факту]** → первый шаг — пробный тест компиляции схемы и
  валидации тела; версия фиксируется по результату.
- **[Инлайнинг схем раздувает JSON]** → ограничение глубины 32 и отказ при циклах; схемы хранятся в
  базе один раз на ревизию.
- **[mTLS нельзя проверить через TestServer]** → юнит-тест на уровне `HttpContext`; реальная проверка
  цепочки остаётся обязанностью хостинга (ADR §13).
- **[Журнал растёт бессрочно]** → зафиксировано в ADR §11.2, политика хранения здесь не вводится.
- **[Порядок проверок влияет на коды ответов]** → порядок зафиксирован в D4 и покрыт тестами.
- **[Лимит на канал с разными ревизиями]** → ключ партиции включает лимит (D7).

## Migration Plan

1. Миграция `AddInboundDispatch`: колонки настроек в `ContractVersions`, `RequestSchemas` в
   `ContractOperations`, таблица `InboundMessageLogs`.
2. Существующие контракты без очереди остаются активными, но новые публикации без очереди
   отклоняются; для действующего контракта очередь задаётся через API до следующей публикации.
3. Проверка: `dotnet build`, `dotnet test`, ручной запуск и вызов активной операции.
4. Откат: revert изменения; таблица журнала удаляется вместе с базой разработки.

## Open Questions

- Настройки отдельной операции и признак `enabled` — следующее изменение (ADR §7.3, §15.2).
- Политика хранения журналов и шифрование — ADR §20.
