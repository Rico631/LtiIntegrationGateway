# Design

## Context

См. `proposal.md` (Why). Состояние, влияющее на подход:

- шина поднята: `AddGatewayRebus` с in-memory транспортом на очереди `lti.gateway.outbound`,
  собственный `ProtobufSerializer`, реестр типов; обработчиков сообщений пока нет;
- конфигурация каналов есть: ревизии со статусами, допустимые методы и шаблоны путей, политика
  повторов, тип авторизации и ключ конфигурации (`Features/Channels`, `Infrastructure/Persistence`);
- `Contracts/MessageContractValidator` проверяет обязательные поля `OutboundRequest`;
- продуктовых маршрутов, HTTP-инфраструктуры, состояния операций и журнала нет;
- по ADR §8.2 исход HTTP-вызова никогда не является исключением, по §8.8 адрес доставки результата
  берётся из `rbs2-return-address` и проверяется по конфигурации, по §8.10 повтор с тем же
  `message_id` не вызывает внешнюю систему.

Проверено по исходникам Rebus: `IRoutingApi.Send(string destinationAddress, object message,
IDictionary<string,string> optionalHeaders = null)`; `Headers.SenderAddress` и
`Headers.ReturnAddress` — константы имён заголовков.

## Goals / Non-Goals

**Goals:**

- обработка `OutboundRequest` от проверок до отправки результата;
- единая точка расчёта исхода вызова и кодов отказа;
- состояние операции и журнал, пригодные для разбора инцидентов;
- отсутствие сетевого вызова при любой ошибке проверок.

**Non-Goals:**

- mTLS и пул обработчиков по сертификату (ADR §7.7) — следующий change;
- фоновый диспетчер недоставленных результатов;
- входящий контур, управляющий API, наблюдаемость.

## Decisions

### D1. Один обработчик сообщения, шаги — отдельными классами

`Features/Outbound/OutboundRequestHandler : IHandleMessages<OutboundRequest>` выполняет шаги
последовательно, вызывая:

```text
ValidateOutboundRequest   проверка полей сообщения и настроек (без БД)
ResolveSenderIdentity     product_id + rbs2-sender-address по ProductRoutes
LoadActiveChannel         активная ревизия канала
ValidateChannelRequest    метод и путь по ревизии
ResolveAuthorization      заголовки авторизации из ISecretStore
ExecuteHttpCall           HTTP-вызов с повторами
RecordOperation           операция + журнал в одной транзакции
PublishResult             результат в очередь отправителя
```

Шаги — обычные классы с конструкторной инъекцией, как в `Features/Channels`; медиатор не вводится.

**Уточнение при реализации:** обработчик разделён на транспортный адаптер
`OutboundRequestHandler : IHandleMessages<OutboundRequest>` (читает `rbs2-sender-address` и
`rbs2-return-address` из `MessageContext.Current.Headers`) и сценарий
`ProcessOutboundRequestHandler`, который принимает `ProcessOutboundRequestCommand` с адресами.
Так сценарий проверяется без ambient-контекста Rebus, а чтение заголовков остаётся в одном месте.
Валидация полей сообщения выполняется первым шагом сценария через статический
`MessageContractValidator`; остальные шаги — `ResolveSenderIdentity`, `LoadActiveChannel`,
проверки метода и пути (`RelativePathMatcher`), `ResolveAuthorization`, `ExecuteHttpCall`,
`OutboundOperationRecorder` и `PublishOutboundResultHandler`.

**Почему один обработчик:** порядок шагов — часть контракта (ADR §8.2), и разносить его по
нескольким обработчикам шины значило бы терять единый контекст операции и корреляцию.

**Почему шаги отдельными классами:** каждый шаг проверяется своим тестом, а обработчик остаётся
читаемым и не превращается в один длинный метод.

### D2. Порядок проверок фиксирован и завершает обработку без сети

```text
1. поля сообщения (Contracts/MessageContractValidator)
2. продукт и адрес отправителя    -> PRODUCT_NOT_ALLOWED / INVALID_REQUEST
3. активная ревизия канала        -> CHANNEL_NOT_ACTIVE / CHANNEL_NOT_ALLOWED
4. метод и путь                   -> METHOD_NOT_ALLOWED / PATH_NOT_ALLOWED
5. тип авторизации и значение      -> AUTH_TYPE_UNSUPPORTED / SECRET_NOT_CONFIGURED
6. состояние идемпотентности       -> повтор без вызова
```

Отказ на шагах 1–5 формирует `OutboundResult` с `outcome = GATEWAY_REFUSED` и кодом; запись в
журнал делается, чтобы отказ был виден при разборе, но HTTP-вызов не выполняется.

**Почему отказ тоже пишется в журнал:** иначе «запрос пришёл и ничего не произошло» невозможно
отличить от «запрос не дошёл».

### D3. Продуктовые маршруты — минимальная конфигурация

```text
ProductRoute   ProductId (уникально), AllowedChannels (строки), AllowedQueueAddresses (строки)
```

Срез `Features/ProductRoutes/RegisterProductRoute` и чтение по `product_id`. Проверка:
`rbs2-sender-address` должен быть в разрешённых адресах продукта, канал — в разрешённых каналах,
адрес доставки (`rbs2-return-address`) — тоже в разрешённых адресах.

**Почему в этом change:** без маршрутов продуктов нельзя выполнить ADR §8.8 — идентичность и
адресация результата. Это часть исходящего контура, а не отдельная функция.

### D4. Повторы — явный цикл, а не статическая политика Resilience

Попытки выполняются циклом: задержки берутся из правил политики канала, проверяется общий предел,
учитывается `Retry-After` для `429`/`503`, `POST`/`PATCH` повторяются только при `idempotency_key`.

**Почему не `Microsoft.Extensions.Http.Resilience` (ADR §2):** политика задаётся в базе для каждого
канала и содержит список задержек и признаки совпадения; статическая политика на именованный
`HttpClient` этого не выражает, а собирать её на каждый канал означало бы держать фабрику политик
вместо простого цикла. Решение осознанно отклоняется от стека и фиксируется здесь.

**Почему `AllowAutoRedirect = false`:** ответ `3xx` — это ответ внешней системы, а не приглашение
шлюзу идти по чужому адресу (ADR §8.7).

### D5. Таймаут попытки, а не клиента

`HttpClient.Timeout` не используется; на каждую попытку создаётся `CancellationTokenSource` с
таймаутом из ревизии канала. Общий предел проверяется перед каждой задержкой.

**Почему:** один общий таймаут клиента смешивал бы таймаут попытки и общий предел, а их значения
задаются независимо.

### D6. Авторизация: интерфейс хранилища секретов и набор типов

`Infrastructure/Security/ISecretStore` с реализацией `ConfigurationSecretStore` поверх
`IConfiguration` (переменные окружения). `ResolveAuthorization` поддерживает `none`, `bearer`,
`api_key` (заголовок или query-параметр), `basic`; тип `client_certificate` отклоняется кодом
`AUTH_TYPE_UNSUPPORTED` до появления mTLS-поддержки.

**Почему интерфейс, а не прямое чтение конфигурации в шаге:** тесты подставляют хранилище без
переменных окружения, а замена на внешнее хранилище секретов не затронет сценарий.

### D7. Состояние операции и журнал — две таблицы с разными обязанностями

```text
OutboundOperation   MessageId (уникальный), ProductId, ChannelName, Status (Accepted/InProgress/Completed),
                    Outcome, HttpStatusCode, ErrorCode, AttemptCount, ReturnAddress, CreatedAt, CompletedAt
OutboundMessageLog  MessageId, ProductId, ChannelName, RequestBody, ResponseBody, ContentType,
                    HttpMethod, RelativePath, AttemptCount, Outcome, DeliveryStatus (pending/sent)
```

Операция и журнал пишутся в одной транзакции **до** попытки отправки результата; после успешной
отправки `DeliveryStatus` меняется на `sent`.

**Почему не одна таблица:** состояние операции читается часто и меняется по шагам, журнал —
почти неизменяемая запись для разбора; смешивание дало бы либо лишние обновления журнала, либо
потерю состояния.

**Почему журнал выполняет роль outbox:** ADR §8.9 фиксирует, что отдельная таблица не создаётся;
фоновый диспетчер появится отдельным change и будет читать `DeliveryStatus = pending`.

### D8. Идемпотентность через уникальный индекс

Уникальный индекс по `MessageId`. При повторном сообщении:

- операция другого продукта → `PRODUCT_NOT_ALLOWED` (запрос не выполняется);
- `Completed` → сохранённый результат отправляется на адрес из текущего сообщения, вызова нет;
- `InProgress` → второй вызов не запускается, результат придёт по завершении первой обработки;
- гонка двух доставок разрешается конфликтом вставки (`DbUpdateException` по уникальному индексу):
  проигравший читает существующую операцию и действует по её состоянию.

**Почему не блокировка в памяти:** обработчики могут выполняться параллельно и в разных
экземплярах; уникальный индекс — единственная гарантия, не зависящая от процесса.

### D9. Тесты: подменяемый HTTP-обработчик и короткие задержки

HTTP-вызов тестируется через `HttpMessageHandler`, который возвращает заранее заданные ответы или
бросает сетевую ошибку; задержки в тестовой политике — единицы миллисекунд, чтобы тесты не ждали
секунды. Шина в тестах — собственный in-memory bus, как в тестах сериализации.

**Почему не реальный сервер:** проверяется наша логика повторов и исходов, а не сеть.

## Risks / Trade-offs

- **[Тип заголовков входящего сообщения внутри обработчика]** → проверено при реализации:
  `MessageContext.Current` (`Rebus.Pipeline`) даёт `Headers` входящего сообщения; чтение вынесено в
  `OutboundRequestHandler`.
- **[Отклонение от пакета Resilience]** → политика повторов реализована вручную; покрыта тестами
  на задержки, `Retry-After`, общий предел и запрет повтора `POST` без ключа.
- **[`api_key` без имени заголовка]** → ревизия хранит только `HeaderName`; если он не задан,
  значение передаётся query-параметром `api_key`, иначе — заголовком с указанным именем.
- **[Долгие повторы занимают воркер]** → тесты используют миллисекундные задержки, в конфигурации
  значения задаются осознанно; ограничение зафиксировано в ADR §7.6.
- **[Тело ответа в журнале]** → размер базы растёт; это уже зафиксированное решение ADR §13.
- **[Без диспетчера результат может не дойти]** → окно между коммитом и отправкой остаётся;
  закрывается следующим change.

## Migration Plan

1. Новая миграция добавляет `OutboundOperations`, `OutboundMessageLogs`, `ProductRoutes`;
   применяется при старте.
2. Проверка: `dotnet build`, `dotnet test`, затем запуск приложения — обработчик регистрируется,
   шина стартует.
3. Откат: revert коммита; таблицы удаляются вместе с базой разработки, данных в промышленной среде
   ещё нет.

## Open Questions

- Нужно ли хранить в операции сериализованный `OutboundResult` целиком (сейчас тело ответа лежит в
  журнале, а операция хранит исход и код) — решается вместе с фоновым диспетчером доставки.
