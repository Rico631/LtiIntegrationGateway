# Proposal

## Why

Проверить контур шлюза вживую сейчас нечем: оба направления покрыты только автотестами на подделках
(`RecordingBus`, `RecordingHttpMessageHandler`), а живого контура, где продукт и внешняя система
действительно обмениваются сообщениями через PostgreSQL-транспорт и ходят HTTP через шлюз, нет.
Ошибки конфигурации — канал, маршрут продукта, режим `SYNC`, политика повторов — воспроизводятся
вручную и не видны в dashboard.

## What Changes

- Два dev-сервиса в каталоге `simulation/`, запускаемые из AppHost:
  - `Simulation.Product` — продукт: участник шины на очереди `product.inbox`. При старте сам
    регистрирует конфигурацию шлюза через управляющий API (канал, два inbound-канала с контрактами,
    маршрут продукта) и ждёт её применения; затем раз в 5 секунд публикует `OutboundRequest`
    `POST /customer`, принимает `OutboundResult` и `InboundMessage`, в режиме `SYNC` отвечает
    `InboundResponse`. Каждое сообщение пишется в лог.
  - `Simulation.Integration` — внешняя система: `POST /customer` для исходящего контура и цикл вызовов
    шлюза раз в 5 секунд — `POST /order` (асинхронный канал) и `GET /order/{orderid}` (синхронный).
    Запросы и ответы пишутся в лог.
- Два OpenAPI-контракта продукта в `simulation/contracts/`: `product-orders-async.json`
  (`POST /order`) и `product-orders-sync.json` (`GET /order/{orderid}`). Режим ответа — свойство
  inbound-канала, поэтому это два документа и два канала; оба встроены в сборку продукта и видны
  в его Swagger.
- Порядок запуска задаётся в AppHost: `management` (готов) → оба `flow-*` (готовы) → `product`
  (готов после регистрации конфигурации) → `integration`.
- Пакет `Microsoft.AspNetCore.OpenApi` и Swagger UI в обоих сервисах: `/openapi/v1.json` и `/swagger`.
- Новый общий проект `src/LtiIntegrationGateway.Messaging`: `ProtobufSerializer` и
  `ProtobufMessageRegistry` переезжают туда из Flow. Шлюз и симуляция используют один формат шины.
- Удаляются `simulation/bootstrap.ps1` и `simulation/scenario.ps1`, а также эндпоинты `/simulation/*`:
  контур работает постоянно, пока запущен AppHost, и проверяется по логам и журналам шлюза.
- Проекты симуляции подключаются к `LtiIntegrationGateway.slnx` отдельной папкой `/simulation/`,
  чтобы их поломки ловились общей сборкой.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

Нет. Поведение шлюза и формат сообщений не меняются: добавляется dev-контур, а перенос сериализатора
не меняет наблюдаемого поведения. Wire-профиль уже зафиксирован в спеке `message-serialization`,
поэтому изменение объявляет `skip_specs: true`.

## Impact

**Контракты.** `.proto` не меняются. Добавляются OpenAPI-документы симуляции — внутренние, никуда не
публикуются.

**Код.** Новый проект `src/LtiIntegrationGateway.Messaging`; перенос двух файлов из
`Flow/Infrastructure/Rebus` и правка ссылок в Flow и тестах; два проекта в `simulation/`; правки
`AppHost`, `slnx`, общих файлов пакетов.

**Зависимости.** Направление зависимостей только «симуляция → прод»: симуляция ссылается на
`Contracts`, `Messaging`, `Core` и `ServiceDefaults`; Flow о симуляции не знает, в прод-манифесты
ничего не добавляется. Добавляется `Microsoft.AspNetCore.OpenApi`, `Microsoft.OpenApi` опускается до
2.12.2 (совместимость с генератором платформы) — обоснование в `design.md` (D11).

**Эксплуатация.** Только локальный контур AppHost. dev-контур станет тяжелее: к шести репликам
сервисов добавятся два сервиса; обмен идёт постоянно, пока AppHost запущен.

**Безопасность.** Симуляция использует dev-ключ управляющего API; значения секретов не появляются,
внешний вызов идёт без авторизации (`auth_type = none`).

## Критерии успеха

- `dotnet build LtiIntegrationGateway.slnx` собирает все проекты, существующие тесты зелёные после
  переноса сериализатора.
- AppHost запускает ресурсы в порядке `management` → `flow-*` → `product` → `integration`; все видны
  в dashboard с состоянием готовности.
- На чистой базе продукт сам создаёт конфигурацию, а повторный запуск не падает и не ломает её.
- Все три сценария наблюдаемы без ручных шагов: outbound (`POST /customer` → `OutboundResult` в лог
  продукта), inbound `ASYNC` (`Sent` в `InboundMessageLogs`), inbound `SYNC` (`Replied` и тело
  сгенерированного заказа).
- Скриптов в репозитории нет; ни `README.md`, ни артефакты OpenSpec на них не ссылаются.

## Исключено из объёма

- Негативные кейсы конфигурации (чужой канал, чужой продукт), нагрузочные сценарии, UI симуляции.
- Автоматический запуск сценария в CI и прод-манифесты.
- OAuth2 и клиентские сертификаты в симуляции: канал использует `auth_type = none`.

## Допущения

- Имена: интеграция `bank-a`, продукт `product`, канал `http` (outbound), `product-orders-async`
  и `product-orders-sync` (inbound). Оба входящих сценария идут через `flow-bank-a`.
- Адреса сервисов, адрес внешней системы и ключ API передаются из AppHost переменными окружения, а не
  зашиты в код.
