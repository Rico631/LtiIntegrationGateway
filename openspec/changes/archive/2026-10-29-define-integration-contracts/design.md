# Design

## Context

См. `proposal.md` (Why). Состояние, влияющее на подход:

- производственный проект `src/LtiIntegrationGateway` содержит только `Program.cs`,
  `Infrastructure/Persistence/GatewayDbContext.cs` и настройки; каталога `Protos` нет;
- в `csproj` один пакет — `Microsoft.EntityFrameworkCore.Sqlite` 10.0.14;
- ADR §3 предполагает `Protos/v1/` с тремя файлами, но `channel_management.proto` и
  `contract_management.proto` относятся к управляющему API и в этот change не входят;
- по ADR §5.3 выбран тулчейн `Google.Protobuf` + `Grpc.Tools`; `protobuf-net` отклонён, потому
  что несовместим с gRPC JSON transcoding;
- по ADR §4.4 контракт распространяется только как `.proto`, профиль кодирования обязан быть
  описан внутри файла.

Проверенные на момент планирования версии: `Google.Protobuf` 3.36.2 (последняя стабильная;
3.37.0 существует только как rc), `Grpc.Tools` 2.85.0.

## Goals / Non-Goals

**Goals:**

- один нормативный `.proto` для интеграционных сообщений с профилем кодирования в шапке;
- генерация C#-типов при сборке, без ручного дублирования DTO;
- тесты, фиксирующие наблюдаемое поведение контракта: обязательность полей, body как bytes,
  повторы query-параметров, различие исходов, профиль ProtoJSON, запрет `Any`.

**Non-Goals:**

- `ISerializer` для Rebus, реестр типов, заголовки `rbs2-*` в коде;
- gRPC-сервисы и JSON transcoding;
- управляющие контракты (`channel_management`, `contract_management`);
- публикация пакета контрактов.

## Decisions

### D1. Один файл `Protos/v1/integration_messages.proto`

`package lti.gateway.messages.v1`, `csharp_namespace
LtiIntegrationGateway.Contracts.Messages.V1`, `syntax = "proto3"`.

Сообщения: `OutboundRequest`, `OutboundResult`, `InboundMessage`, `QueryParameter`, enum
`Outcome`.

**Почему один файл:** все три сообщения — части одного контракта обмена, который потребитель
забирает целиком; разнесение по файлам добавило бы импорты без пользы. Управляющие контракты
появятся своими файлами, когда появится управляющий API.

**Нумерация полей** — по порядку таблиц ADR §8.3, §8.5, §9.3: номера фиксируются один раз и
дальше только добавляются. Пустых «зарезервированных на будущее» номеров не вводим — `reserved`
появится тогда, когда появится удалённое поле.

### D2. Генерация через `Grpc.Tools` с `GrpcServices="None"`

В `csproj`:

```xml
<ItemGroup>
  <PackageReference Include="Google.Protobuf" Version="3.36.2" />
  <PackageReference Include="Grpc.Tools" Version="2.85.0" PrivateAssets="All" />
</ItemGroup>

<ItemGroup>
  <Protobuf Include="Protos\v1\integration_messages.proto" GrpcServices="None" />
</ItemGroup>
```

`GrpcServices="None"` означает «только сообщения, без клиента и сервера» — gRPC-сервисы
добавит change про управляющий API, и тогда значение изменится, а контракт сообщений — нет.

**Почему `PrivateAssets="All"` у `Grpc.Tools`:** это build-time инструмент, он не должен
попадать в зависимости потребителей.

**Сгенерированные файлы не редактируются** — они создаются в `obj/` и не попадают в репозиторий.

### D3. Типы полей

| Решение | Обоснование |
|---|---|
| `bytes body`, `bytes response_body` | формат задаётся `content_type`, содержимое может быть не только JSON; сохраняется исходное представление чисел |
| `optional` для `content_type`, `correlation_id`, `idempotency_key`, `http_status_code`, `error_code`, `error_message`, `operation_id`, `external_message_id` | в ProtoJSON отсутствие поля — значимый сигнал, а не «значение по умолчанию» |
| `repeated QueryParameter query_parameters` | сохраняет порядок и повторы, в отличие от `map<string,string>` |
| `google.protobuf.Timestamp received_at` | предсказуемое представление момента времени в ProtoJSON |
| `enum Outcome` с `OUTCOME_UNSPECIFIED = 0` | закрытое множество из трёх исходов, признак «не задано» отделён от значений |
| `int32 http_status_code`, `int32 attempt_count` | статус и число попыток не выходят за пределы `int32` |

`google.protobuf.Any` не используется; `Struct` и `Value` не используются для тел.

### D4. Профиль кодирования — нормативный комментарий в шапке `.proto`

В шапке фиксируется: ProtoJSON, camelCase на проводе, `bytes` → base64, `int64` → строка, enum
→ имя, неизвестные поля игнорируются, заголовок `rbs2-msg-type` содержит полное имя сообщения.

**Почему в файле, а не только в ADR:** потребитель получает только `.proto`; если профиль не
описан рядом с контрактом, он сгенерирует типы и выберет бинарный protobuf.

**Почему комментарий, а не отдельный документ:** рядом с определениями сообщений его нельзя
потерять при копировании файла.

### D5. Тесты профиля используют `JsonFormatter`/`JsonParser` напрямую

Сериализатора Rebus ещё нет, поэтому тесты создают `JsonParser` с `IgnoreUnknownFields = true` и
проверяют фактическое поведение: camelCase-имена, base64 для `bytes`, сохранение порядка
`query_parameters`, игнорирование неизвестного поля, различие «поле отсутствует» и «поле задано».

**Почему не ждать следующего change:** профиль — часть публикуемого контракта. Если он не
проверен сейчас, следующий change будет подгонять сериализатор под то, что случайно получилось.

### D6. Запрет `Any` проверяется по дескрипторам

Тест обходит дескрипторы всех сообщений окружения и падает, если встречает поле типа
`google.protobuf.Any`.

**Почему не текстовый поиск по файлу:** проверка по дескриптору не зависит от форматирования и
ловит `Any` и во вложенных сообщениях.

## Risks / Trade-offs

- **[Несовпадение версий `Grpc.Tools` и `Google.Protobuf`]** → если сгенерированный код
  потребует более новый рантайм, версия `Google.Protobuf` поднимается до указанной сборкой; обе
  версии фиксируются в проекте.
- **[Неверный тип поля после публикации]** → номера и типы сверяются с ADR построчно; смена типа
  потребует `v2`, поэтому проверка делается до публикации контракта потребителям.
- **[Профиль описан дважды — в ADR и в `.proto`]** → расхождение возможно; тесты D5 падают при
  изменении поведения, а ADR ссылается на `.proto` как на нормативный источник.
- **[Слишком узкий первый набор полей]** → сообщения содержат только то, что описано в ADR;
  добавление полей — совместимое изменение, поэтому задержка с расширением дешевле, чем удаление
  неверного поля.

## Migration Plan

1. Контракт публикуется впервые, потребителей нет; миграция не требуется.
2. Проверка: `dotnet build` (генерация типов) и `dotnet test` (тесты контракта).
3. Откат: revert коммита; сгенерированные файлы в `obj/` пересоздаются автоматически.

## Open Questions
