# Proposal

## Why

Контрактов сообщений в проекте не существует: есть хост и тестовый контур, но нет ни одного
`.proto`, поэтому продуктам нечего генерировать, а шлюзу нечего сериализовать. ADR v1.3
(§5.3–5.5, §8.3, §8.5, §9.3) уже определяет состав полей, имена, типы и профиль кодирования —
их нужно материализовать в `.proto` и проверить тестами **до** реализации сериализации Rebus,
иначе каждый потребитель выберет собственный формат тела и совместимость будет потеряна
безвозвратно.

## What Changes

- Добавляется `src/LtiIntegrationGateway/Protos/v1/integration_messages.proto`: сообщения
  `OutboundRequest`, `OutboundResult`, `InboundMessage`, вспомогательный `QueryParameter` и
  перечисление `Outcome`.
- В шапке `.proto` фиксируется нормативный профиль кодирования: ProtoJSON, camelCase на
  проводе, `bytes` как base64, `int64` строкой, enum именем, неизвестные поля игнорируются,
  заголовок типа `rbs2-msg-type` содержит полное имя сообщения.
- В проект добавляется генерация C#-типов из `.proto` (`Google.Protobuf` + `Grpc.Tools`,
  `GrpcServices="None"` — gRPC-сервисы появятся отдельным change).
- Добавляются тесты на сгенерированные типы: round-trip через `JsonFormatter`/`JsonParser`,
  сохранение порядка и повторов `query_parameters`, кодирование `bytes`, игнорирование
  неизвестных полей, обязательность ключевых полей.
- Добавляется проверка обязательных полей `OutboundRequest` — небольшой валидатор рядом с
  контрактом, чтобы требование «невалидный запрос не выполняется» было реализовано и покрыто
  тестом уже в этом change, а не осталось декларацией в спецификации.
- **BREAKING** для потребителей нет: контракт публикуется впервые.
- Правило распространения: `.proto` — единственный артефакт, клиенты генерируют типы сами
  (ADR §4.4); версия контракта — `package lti.gateway.messages.v1`.

### Исключения из объёма

- `ISerializer` для Rebus и реестр типов — следующий change (`rebus-protobuf-serialization`);
- управляющие `.proto` (`channel_management.proto`, `contract_management.proto`) и gRPC
  JSON transcoding — change про управляющий API;
- конфигурация Rebus, очереди, обработчики;
- модель данных и EF Core-сущности;
- публикация пакета контрактов (по ADR пакет не создаётся).

### Риски

- **Неправильный тип поля дорог в исправлении.** После публикации `.proto` смена типа поля
  требует `v2`. Смягчение: поля сверяются с таблицами ADR §8.3, §8.5, §9.3 построчно, а
  решения по `bytes`/`repeated`/`optional` зафиксированы в design с обоснованием.
- **Расхождение профиля кодирования.** Если профиль останется только в ADR, клиент может
  сгенерировать типы и выбрать бинарный protobuf. Смягчение: профиль в шапке `.proto` и
  тест, который падает при расхождении формата на проводе.
- **Версии `Grpc.Tools`/`Google.Protobuf`.** Генерация зависит от версии тулчейна; версия
  фиксируется в проекте.
- **Преждевременная фиксация полей, которые понадобятся позже.** Состав сообщений взят
  строго из ADR; всё, чего там нет (`headers`, абсолютный URL, секреты), в контракт не
  попадает.

### Проверяемые критерии успеха

- `dotnet build LtiIntegrationGateway.slnx` проходит, C#-типы генерируются из `.proto`;
- `dotnet test` проходит, включая тесты round-trip и профиля кодирования;
- в сгенерированном `OutboundRequest` присутствуют `message_id`, `product_id`, `channel_name`,
  `relative_path`, `http_method`, `body`, `query_parameters`;
- `InboundMessage` содержит `http_method`, `relative_path`, `route_template`, `body` и не
  содержит `path_parameters`;
- тело на проводе — ProtoJSON: `bytes` в base64, поля в camelCase, неизвестное поле не ломает
  разбор;
- в шапке `.proto` описан профиль кодирования и версия пакета.

## Capabilities

### New Capabilities

- `message-contracts`: контракты сообщений Rebus между продуктами и шлюзом — состав полей,
  обязательность, представление тела и query-параметров, профиль кодирования и правила
  совместимости.

### Modified Capabilities

Нет: существующая `gateway-host` описывает поведение хоста и не меняется.

## Impact

- Код: `src/LtiIntegrationGateway/Protos/v1/integration_messages.proto`,
  `src/LtiIntegrationGateway/Contracts/MessageContractValidator.cs`,
  `LtiIntegrationGateway.csproj` (ссылки `Google.Protobuf`, `Grpc.Tools`, элемент `Protobuf`).
- Тесты: новые тесты в `src/LtiIntegrationGateway.Tests` для сгенерированных типов.
- Зависимости: `Google.Protobuf`, `Grpc.Tools` (версии фиксируются в проекте).
- Внешние потребители: контракт публикуется впервые; продуктов, которые его уже используют,
  нет.
- Rebus, хранилище, управляющий API не затрагиваются.
