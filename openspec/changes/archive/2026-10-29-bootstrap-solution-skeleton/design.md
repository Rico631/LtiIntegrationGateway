# Design

## Context

См. `proposal.md` (Why). Фактическое состояние, влияющее на подход:

- решение `LtiIntegrationGateway.slnx` уже содержит производственный проект
  `src/LtiIntegrationGateway/LtiIntegrationGateway.csproj` — подключать его не нужно;
- `Program.cs` целиком шаблонный: `AddOpenApi()`, `MapOpenApi()`, `UseHttpsRedirection()`,
  `GET /weatherforecast` и запись `WeatherForecast`;
- тестового проекта, `Directory.Build.props` и `.editorconfig` нет;
- целевая платформа `net10.0`; в проекте уже зафиксирован
  `Microsoft.AspNetCore.OpenApi` 10.0.14, то есть версии пакетов ведутся по ветке 10.0.x;
- по ADR v1.3 терминация TLS и ограничение размера тела выполняются на уровне nginx, а
  health/readiness с проверками зависимостей остаются открытым вопросом (§20).

Проверенные версии пакетов на момент планирования: `TUnit` 1.76.45,
`Microsoft.AspNetCore.Mvc.Testing` 10.0.14, `Microsoft.EntityFrameworkCore.Sqlite` 10.0.14.

## Goals / Non-Goals

**Goals:**

- получить хост без шаблонного кода, с одной liveness-пробой;
- получить работающий тестовый контур на TUnit, пригодный для следующих изменений;
- обеспечить fail-fast при отсутствии строки подключения к хранилищу;
- зафиксировать помощник тестов для SQLite `:memory:` до появления первой модели данных.

**Non-Goals:**

- readiness-проба с проверками зависимостей, метрики, OTel — открытые вопросы ADR §20;
- модель данных, сущности EF Core, миграции;
- конфигурация Kestrel (лимиты, порты) и TLS — зона nginx;
- аутентификация, Rebus, gRPC, OpenAPI-валидация.

## Decisions

### D1. Liveness через встроенные health checks, а не отдельный эндпоинт

`builder.Services.AddHealthChecks()` и `app.MapHealthChecks("/health/live", new
HealthCheckOptions { Predicate = _ => false })`. Предикат `false` отключает все
зарегистрированные проверки, поэтому проба не обращается к базе, Rebus и внешним системам.

**Почему не `MapGet("/health/live", ...)`:** readiness с проверками зависимостей появится
следующим этапом, и тогда понадобится ровно этот механизм. Один инструмент вместо двух.

**Почему предикат, а не отдельный пустой набор:** предикат гарантирует, что будущие проверки,
зарегистрированные для readiness, не попадут в liveness автоматически.

### D2. Явная проверка строки подключения после `builder.Build()`

Строка читается через `app.Configuration.GetConnectionString("Gateway")` сразу после
`builder.Build()` и до маппинга эндпоинтов; при отсутствии или пустом значении выбрасывается
`InvalidOperationException` с именем ключа `ConnectionStrings:Gateway`. Регистрация
`DbContext` получает строку из `IConfiguration` через фабрику, чтобы оба места читали один и
тот же окончательный набор источников.

**Почему не до `builder.Build()` (первоначальный вариант):** проверка выполняется до того, как
применяются переопределения конфигурации, — обнаружилось на тесте fail-fast, где
`WebApplicationFactory` подменяет источники уже после чтения. Проверка после `Build()` видит
окончательную конфигурацию и при этом всё ещё предшествует обслуживанию запросов.

**Почему не `Options` + `ValidateOnStart()`:** настройка одна и не имеет структуры; класс
настроек был бы обёрткой без содержания. Переход на `ValidateOnStart()` — когда настроек
станет несколько (каналы, лимиты, очереди).

**Почему не «падение при первом использовании»:** контракт EF Core бросит исключение только
при создании `DbContext`, то есть после старта, что противоречит требованию спеки о падении
на запуске.

### D3. Регистрация EF Core + SQLite без сущностей

`builder.Services.AddDbContext<GatewayDbContext>(o => o.UseSqlite(connectionString))`, где
`GatewayDbContext` пуст (`OnModelCreating` не переопределяется).

**Почему сейчас:** это единственный способ проверить, что провайдер SQLite установлен и
строка подключения читается, до появления первой сущности. Пустой контекст не создаёт схему
и никого не обязывает.

**Почему не отложить регистрацию:** тогда fail-fast из D2 нечем подтвердить — проверка была бы
проверкой строки ради строки.

### D4. Удаление шаблонного OpenAPI и HTTPS-редиректа

Вместе с шаблонным кодом удаляются `AddOpenApi()`, `MapOpenApi()`, пакет
`Microsoft.AspNetCore.OpenApi` и `UseHttpsRedirection()`.

**Почему OpenAPI-пакет уходит:** он относится к генерации OpenAPI-документа для минимальных
API. Управляющий API по ADR §5.1 — gRPC с JSON transcoding, и его документация решается в
своём change. Возврат пакета — одна строка, если он понадобится.

**Почему убирается `UseHttpsRedirection`:** TLS терминируется на ingress (ADR §13), а редирект
внутри приложения ломает health-пробы и тесты, которые обращаются по HTTP.

### D5. Раскладка тестового проекта

`src/LtiIntegrationGateway.Tests` с каталогами `Features/`, `Infrastructure/`, `TestSupport/`
и `ProjectReference` на производственный проект; проект добавляется в `.slnx` командой
`dotnet sln ... add` (поддержка `.slnx` проверена: `dotnet sln LtiIntegrationGateway.slnx
list` возвращает текущий проект).

### D6. Тестирование хоста через `WebApplicationFactory<Program>`

- в конце `Program.cs` добавляется `public partial class Program;` — без этого
  `WebApplicationFactory` не находит точку входа при top-level statements;
- фабрика создаётся на тест, конфигурация переопределяется через `WithWebHostBuilder`
  (строка подключения — SQLite `:memory:`), это же позволяет запускать тест «запуск без
  строки подключения», ожидая исключение;
- для проверки логов используется собственный `ILoggerProvider`, собирающий записи в память;
  проверяется отсутствие значения строки подключения;
- помощник `TestSupport/SqliteInMemoryDatabase` инкапсулирует требование ADR §11.3: соединение
  `Data Source=:memory:` открыто на всё время теста, иначе база теряется между операциями.

**Почему не реальный сервер и не браузерный драйвер:** проверяемое поведение — контракт
HTTP-эндпоинтов и старт приложения, для этого достаточно in-process хоста.

### D7. Содержимое `LtiIntegrationGateway.http`

Файл не удаляется: в нём остаётся единственный запрос к `GET /health/live` с переменной
`HostAddress`. Это ручная проверка пробы без запуска тестов.

## Risks / Trade-offs

- **[Пакет `Microsoft.AspNetCore.OpenApi` может понадобиться для gRPC-транскодинга]** →
  возвращается в change, посвящённом управляющему API; удаление сейчас не создаёт блокировки.
- **[Пустой `GatewayDbContext` выглядит как «заготовка на будущее»]** → в задаче фиксируется
  причина (проверка провайдера и строки подключения) и запрет добавлять сущности до среза,
  который их использует.
- **[`WebApplicationFactory` и top-level statements]** → требование `public partial class
  Program;` вынесено отдельной задачей; без него тесты не компилируются, что видно сразу.
- **[TUnit меняет API между версиями]** → версия фиксируется в проекте; обновление — отдельное
  решение, а не следствие восстановления пакетов.
- **[Проверка «нет секретов в логах» может быть хрупкой]** → проверяется отсутствие конкретной
  строки подключения, а не формат логов целиком.
- **[Liveness без проверок зависимостей]** → сознательный выбор: проба не должна падать из-за
  недоступной БД, иначе оркестратор начнёт перезапускать живой процесс.

## Migration Plan

1. Изменения кода и решения применяются одним коммитом; данных и схемы не затрагивают.
2. Проверка: `dotnet build LtiIntegrationGateway.slnx`, затем `dotnet test`.
3. Ручная проверка: запуск приложения, `GET /health/live` → `200`, `GET /weatherforecast` →
   `404`.
4. Откат: revert коммита; внешних потребителей у шаблонного эндпоинта нет, миграция данных не
   требуется.

## Open Questions

- Нужен ли `Directory.Build.props` с общими свойствами (например `TreatWarningsAsErrors`) до
  появления второго производственного среза — решается в change про контракты, когда станет
  видно, какие свойства действительно общие.
