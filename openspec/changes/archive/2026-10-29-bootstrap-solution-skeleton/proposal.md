# Proposal

## Why

Сейчас репозиторий содержит только шаблон `dotnet new webapi`: `Program.cs` публикует
демонстрационный `/weatherforecast`, тестового проекта нет, а хост не имеет ни одной пробы
состояния. По ADR v1.3 первый этап — исходящий контур, но начинать его нельзя: любая
последующая задача (контракты Protobuf, сериализация Rebus, каналы, HTTP-вызовы) требует
работающего тестового контура и хоста без шаблонного мусора. Этот change создаёт такую
основу, чтобы следующие изменения проверялись тестами, а не «на глаз».

## What Changes

- Из `Program.cs` удаляется шаблонный код: `WeatherForecast`, `GET /weatherforecast`,
  регистрация OpenAPI-документа для шаблона, пример из `LtiIntegrationGateway.http`.
- Добавляется liveness-проба `GET /health/live`: ответ `200` без обращения к базе данных,
  Rebus и внешним системам.
- Добавляется обязательная конфигурация хранилища `ConnectionStrings:Gateway` и минимальная
  регистрация EF Core с SQLite: при отсутствии настройки приложение падает на старте с
  понятным сообщением, а не работает «наполовину». Сущности и миграции в этом change не
  появляются — модель данных придёт вместе со срезами, которые её используют.
- Создаётся тестовый проект `src/LtiIntegrationGateway.Tests` на TUnit, подключается к
  `LtiIntegrationGateway.slnx`; в нём появляются первые тесты хоста и вспомогательный
  `TestSupport` (в том числе готовый помощник для SQLite `:memory:`).
- **BREAKING** (внутри репозитория): эндпоинт `/weatherforecast` исчезает; если кто-то уже
  обращался к нему вручную или в `.http`-файле, обращение перестанет работать.

### Исключения из объёма

- контракты `.proto` и генерация кода (`Grpc.Tools`) — следующий change;
- сериализация Rebus, очереди, обработчики — следующий change;
- модель данных, EF Core-сущности, миграции;
- health/readiness с проверкой зависимостей, метрики, OTel, лимиты Kestrel — открытые
  вопросы ADR §20, здесь только liveness;
- аутентификация, HTTPS-настройки развёртывания, nginx.

### Риски

- **Изменение раскладки решения.** Появление второго проекта и ссылки между ними может
  конфликтовать с настройками IDE или локальными скриптами; проверяется сборкой решения
  целиком и запуском тестов.
- **Выбор версии TUnit.** Тестовый фреймворк молодой, его API менялся между версиями; версия
  фиксируется в проекте, а не подтягивается последней автоматически.
- **EF Core на SQLite до появления сущностей.** Регистрация хранилища без модели данных
  может выглядеть преждевременной; она вводится только чтобы fail-fast по конфигурации и
  помощник тестов существовали до первого среза с БД.

### Проверяемые критерии успеха

- `dotnet build LtiIntegrationGateway.slnx` проходит без ошибок;
- `dotnet test` выполняет тесты проекта `LtiIntegrationGateway.Tests` и они проходят;
- `GET /weatherforecast` возвращает `404`, шаблонного кода в проекте нет;
- `GET /health/live` возвращает `200` при запущенном приложении без настроек внешних систем;
- запуск без `ConnectionStrings:Gateway` завершается ошибкой с явным указанием отсутствующего
  ключа конфигурации;
- в логах старта нет значения строки подключения.

## Capabilities

### New Capabilities

- `gateway-host`: поведение хоста шлюза — запуск, отсутствие демонстрационного API,
  liveness-проба, обязательная конфигурация хранилища и отсутствие секретов в логах.

### Modified Capabilities

Нет: постоянных спецификаций в проекте пока не существует (`openspec/specs` пуст).

## Impact

- Код: `src/LtiIntegrationGateway/Program.cs`, `LtiIntegrationGateway.csproj`,
  `LtiIntegrationGateway.http`; новый проект `src/LtiIntegrationGateway.Tests`.
- Решение: `LtiIntegrationGateway.slnx` (добавление тестового проекта).
- Зависимости: `TUnit` (1.76.45), `Microsoft.AspNetCore.Mvc.Testing`,
  `Microsoft.EntityFrameworkCore.Sqlite`, `Microsoft.Extensions.Diagnostics.HealthChecks`
  (входит в ASP.NET Core); версии фиксируются в проекте.
- Внешние системы: нет. Rebus, gRPC, OpenAPI-валидация не затрагиваются.
- Документация: `README.md` (как собрать и запустить тесты) — единственная правка вне кода.
