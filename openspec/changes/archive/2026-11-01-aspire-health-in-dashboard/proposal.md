# Proposal

## Why

В Aspire dashboard у ресурсов не отображалось состояние здоровья: AppHost не знал, по какому адресу
опрашивать сервис, поэтому были видны только состояние процесса и телеметрия. Неготовность сервиса
(недоступное хранилище, неприменённая схема) обнаруживалась лишь по логам или по ошибкам вызовов.

## What Changes

- AppHost регистрирует HTTP health check для каждого сервисного ресурса: `management` и
  `flow-<integration>` опрашиваются по `/health/ready` (`WithHttpHealthCheck`).
- Состояние пробы отображается в dashboard в колонке Health; проба готовности включает проверку
  хранилища (`DatabaseHealthCheck`, тег `ready`), поэтому недоступная БД делает ресурс нездоровым.
- Продуктовое поведение не меняется: пробы `/health/live` и `/health/ready` уже публиковались и
  описаны в спеке `gateway-host`. Новых требований к продукту нет, поэтому спеки не меняются
  (`skip_specs: true`).

## Impact

**Код.** `src/LtiIntegrationGateway.AppHost/Program.cs` — по одной строке
`.WithHttpHealthCheck("/health/ready")` у management и у каждого flow-ресурса. Пакеты не добавляются:
API входит в `Aspire.Hosting`.

**Эксплуатация.** Изменение действует только в локальном контуре разработки; в Kubernetes AppHost не
разворачивается, прод-манифесты ведутся отдельно.

**Ограничение (поведение Aspire).** При `WithReplicas(2)` dashboard опрашивает не каждый экземпляр:
в проверочном запуске опрашивался один экземпляр на каждый flow-ресурс и обе реплики management.
Это поведение Aspire/DCP, а не приложения; для локальной разработки его достаточно.

## Критерии успеха

- В dashboard у `management`, `flow-bank-a` и `flow-bank-b` отображается состояние здоровья.
- Dashboard периодически запрашивает `/health/ready`, сервисы отвечают `200`.
- При недоступном хранилище ресурс отображается как нездоровый.
