# Proposal

## Why

Интеграции в шлюзе появляются неявно: запись в `Integrations` создаётся при первой изменяющей
операции над ресурсами интеграции (`IntegrationRegistry.GetOrCreateAsync`), а отдельного способа
получить их перечень нет. Оператор не может узнать, какие интеграции существуют и на какой версии
конфигурации они находятся, не имея доступа к базе: список приходится собирать вручную из каналов,
маршрутов и контрактов.

## What Changes

- В управляющий контракт добавляется один read-метод `ListIntegrations`: gRPC-вызов и
  `GET /v1/integrations` через JSON transcoding. Метод не адресуется интеграцией — это ресурс
  верхнего уровня, поэтому scope-поля `integration` в запросе нет.
- Ответ содержит все записи интеграций, упорядоченные по идентификатору: идентификатор, версия
  действующей конфигурации и время появления записи. Пустой список — успешный ответ.
- Создание интеграции остаётся неявным. Новых изменяющих операций, методов получения одной
  интеграции и удаления не вводится; формат идентификатора интеграции на стороне управления
  по-прежнему не проверяется.
- В требованиях фиксируется правило, которое уже действует в коде: обзорные списки (`List*`) не
  пишут аудит управляющих операций. Сейчас требование сформулировано как «каждая управляющая
  операция», что расходится с поведением `ListOutboundChannels` и `ListInboundChannels`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `management-api`: добавляется требование о публикации списка интеграций (ранее перечисления
  интеграций в контракте не было) и уточняется требование об аудите — обзорные списки в аудит не
  попадают.

## Impact

**Контракты.** Изменения `protos/v1/management_api.proto` аддитивны: новый `rpc` и три сообщения,
существующие поля и маршруты не затрагиваются, `package lti.gateway.management.v1` сохраняется.
Публикуемый OpenAPI-документ управляющего API и Swagger UI подхватывают метод автоматически, потому
что строятся из дескриптора контракта.

**Код.** Реализация — в фасаде управляющего API, тем же способом, что и существующие списки каналов;
выборка идёт из `GatewayDbContext.Integrations`. Схема БД, миграции и `IntegrationRegistry` не
меняются, новых зависимостей нет.

**Данные.** Список отражает фактически настроенные интеграции: строка появляется только при первой
успешной настройке, удаления через API нет. Развёрнутые, но ещё не настроенные интеграции в списке
не видны — сервис управления не знает о развёртывании. Строки с идентификатором, не проходящим
шаблон, остаются видимыми: чтение толерантное.

**Безопасность.** Метод требует ключ API на общих основаниях (префикс `/v1`), значения секретов в
ответ не попадают — в `Integrations` их нет.

**Совместимость.** Только добавления: существующие потребители управляющего API не затронуты.

## Критерии успеха

- `GET /v1/integrations` и gRPC `ListIntegrations` возвращают все записи интеграций, упорядоченные по
  идентификатору, с версией конфигурации и временем появления записи.
- На базе без настроенных интеграций ответ успешен и содержит пустой список.
- Операция появляется в OpenAPI-документе и Swagger UI без правок генератора.
- Вызов списка не создаёт записей в аудите управляющих операций.

## Исключено из объёма

- Создание интеграции через API и любая явная регистрация (`CreateIntegration`).
- Получение одной интеграции по идентификатору (`GetIntegration`) и удаление интеграции.
- Проверка формата идентификатора интеграции на стороне управления.
- Счётчики каналов, состояние применения конфигурации, пагинация и фильтры в запросе.

## Допущения

- «Существующие интеграции» означают все записи `Integrations`. Так как запись создаётся в транзакции
  первой настройки и удаления нет, множество записей совпадает с множеством настроенных интеграций.
- Порядок по идентификатору достаточен: количество интеграций измеряется единицами, пагинация не
  требуется.
