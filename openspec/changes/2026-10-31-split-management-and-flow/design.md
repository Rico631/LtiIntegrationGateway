# Design

## Context

Текущее состояние (см. `ARCHITECTURE.md`, разделы 0.3, 0.7, 1, 5, 7): один web-процесс, SQLite через `ConnectionStrings:Gateway`, `Database.Migrate()` при старте (`Program.cs:166-169`), in-memory транспорт Rebus (`RebusConfigurationExtensions.cs:26`), глобальные имена каналов и очередей (`QueueNames`), синхронная активация конфигурации с изменением in-memory каталога маршрутов (`ActivateContractVersionHandler`), health, читающий runtime-журналы из той же БД.

Ограничения, заданные целевой эксплуатацией:

- ArgoCD разворачивает одно приложение, в котором живут сервис управления конфигурацией и N экземпляров сервиса потоков — по одному на интеграцию.
- Каждый сервис работает в двух репликах; реплики management стартуют последовательно.
- Сетевой доступ разделяется на уровне ingress: у каждой интеграции свой ingress. Egress не ограничивается.
- Секреты общие для management и flow; значения берутся из конфигурации окружения.
- Продукт LTI знает интеграции, которые использует, но не знает количества экземпляров и реплик.

## Goals / Non-Goals

**Goals:**

- Разделить монолит на `Management` и `Flow` с сохранением функциональных требований спек.
- Ввести интеграцию как единицу конфигурации, изоляции и адресации.
- Перевести хранилище и транспорт на PostgreSQL, обеспечив корректность при двух репликах.
- Сделать применение конфигурации асинхронным, но ограниченным по времени и наблюдаемым.
- Перенести `.proto` в корень и генерировать контракты один раз.
- Дать локальный контур разработки на Aspire и тесты на реальном PostgreSQL.

**Non-Goals:**

- Egress-политики, egress-прокси, распределённое ограничение частоты.
- Промышленный secret provider, IdP, OAuth2.
- Генерация прод-манифестов из AppHost.
- Изменение состава полей сообщений Rebus.

## Decisions

### D1. Одна база PostgreSQL, разные роли владения

Management и все экземпляры flow работают с одной базой. Management — единственный писатель конфигурации и единственный, кто применяет миграции. Flow читает конфигурацию и пишет runtime-данные. Границы владения дополнительно фиксируются правами: отдельные DB-роли для конфигурации и runtime.

Альтернативы: две базы (потребовала бы контракт снапшота конфигурации и отдельный путь агрегации health); база на интеграцию (N провижинингов и N миграций).

### D2. Интеграция — единица конфигурации

`Integration` — скоуп для каналов, версий контрактов и маршрутов продуктов. Уникальность имён становится составной: `(integration_id, name)`. Маршрут продукта адресуется `(integration_id, product_id)`, поэтому один продукт может работать с несколькими интеграциями. Экземпляр flow обслуживает ровно одну интеграцию, заданную конфигурацией `Gateway:Integration`.

Ключевое следствие: проверки конфликтов маршрутов, разрешённых каналов и владения продуктом выполняются в пространстве интеграции, а не глобально.

### D3. Адресация по интеграции, а не по экземпляру

Входная очередь интеграции — `lti.gateway.<integration>.outbound`, error-queue — `lti.gateway.<integration>.error`. Продукт делает `Send` в очередь интеграции; количество реплик меняет только число конкурирующих потребителей. Состав сообщений не меняется: интеграция передаётся адресом. Flow дополнительно проверяет, что канал принадлежит его интеграции, и отвечает `CHANNEL_NOT_ALLOWED` на чужой канал.

Отклонённые варианты: fan-out по подписке на тип сообщения (Postgres-транспорт копирует сообщение в очередь каждого подписчика — payload одной интеграции попал бы в очередь другой, плюс требование subscription storage у продуктов); единая очередь с роутером (третий деплой и SPOF на входе).

### D4. Rebus: PostgreSQL-транспорт, общая таблица сообщений

Транспорт — `Rebus.PostgreSql` с одной таблицей `messages`; `inputQueueName` различает интеграции. Pub/sub не используется: все взаимодействия — `Send` и `SendRequest`, поэтому subscription storage не нужна. Management шину не использует: он не отправляет и не принимает сообщения, только читает runtime-таблицы для диагностики.

Шина рассматривается как доверенная зона: все участники имеют доступ к таблице сообщений, изоляция строк отсутствует. Изоляция интеграций обеспечивается конфигурацией и раздельными ingress.

Открытый риск: продолжит ли работать `SYNC` входящий режим при двух репликах на одной очереди. Требуется спайк; результат определяет, нужна ли reply-очередь на запрос.

### D5. Применение конфигурации: версия и сверка

Любое изменение, влияющее на действующую конфигурацию интеграции, увеличивает `configuration_version` в той же транзакции. Экземпляр flow периодически (2 секунды) сравнивает действующую версию со своей применённой; при расхождении перестраивает наборы маршрутов, регистрирует endpoints и прогревает кэш схем. Целевое время применения — не более 5 секунд.

Экземпляр пишет в `flow_instance_state` строку `(integration_id, instance_id, applied_version, secret_configured, certificate_expires_at, reported_at)`. Management читает её для диагностики; признак `stale` вычисляется по порогу 15 секунд.

Отклонённые варианты: `LISTEN/NOTIFY` (всё равно требует сверки как страховки); Rebus-событие `ConfigurationChanged` (новый внутренний контракт и порядок сообщений); push из management (нужен service discovery, management становится runtime-зависимостью).

### D6. Инварианты вместо распределённых блокировок

| Инвариант | Механизм |
|---|---|
| одна активная ревизия канала | partial unique index по каналу, `WHERE status = 'Active'` |
| одна активная версия контракта | partial unique index по inbound-каналу, `WHERE status = 'Active'` |
| запись `pending` не доставляется дважды в цикле | `FOR UPDATE SKIP LOCKED` при выборке пачки |
| миграции | только management; database-wide lock EF Core 9+ как страховка |

`DistributedLock` не вводится. Локальные блокировки остаются только для процесс-локального состояния (снимок каталога маршрутов в каждом экземпляре).

Проигравшая гонку транзакция получает нарушение уникального индекса и возвращает `succeeded = false` с проблемой `conflict`. Ответ активации означает «зафиксировано и прошло проверки», а не «маршруты зарегистрированы во всех экземплярах».

### D7. Границы проектов

```text
src/LtiIntegrationGateway.Contracts       генерация C# из protos (Both / None)
src/LtiIntegrationGateway.Core            entities, DbContext, миграции, чтение и проверка OpenAPI,
                                          InboundRouteSetValidator, ISecretStore, Result<T>
src/LtiIntegrationGateway.Management      управляющий API, жизненный цикл конфигурации, аудит, миграции
src/LtiIntegrationGateway.Flow            входящий и исходящий контуры, Rebus, каталог маршрутов
src/LtiIntegrationGateway.ServiceDefaults OTel, health, общие настройки хоста
src/LtiIntegrationGateway.AppHost         Aspire: PostgreSQL, оба сервиса, реплики, dashboard
```

Правило: `Core` содержит только модель данных и чистые проверки — без срезов, DI, ASP.NET и Rebus. Срез принадлежит одному сервису. Общими остаются: модель данных, чтение и проверка OpenAPI-документа, построение и проверка набора маршрутов, абстракции секретов, `Result<T>`.

Причина: `PublishContractVersionHandler` уже использует `OpenApiDocumentReader`, `InboundRouteSetValidator` и `InboundRateLimitOptions`, а flow применяет те же правила при регистрации маршрутов. Дублирование этих правил привело бы к расхождению проверок между сервисами.

### D8. Protobuf: корень репозитория и совместимость

```text
protos/v1/integration_messages.proto
protos/v1/management_api.proto
protos/google/api/*.proto
```

`integration_messages.proto` не меняется: интеграция передаётся адресом очереди. `management_api.proto` получает измерение интеграции — новые поля запросов и пути `/v1/integrations/{integration_id}/...`. Номера существующих полей не переиспользуются, типы не меняются, поэтому protobuf-совместимость на уровне сообщений сохраняется; REST-маршруты меняются несовместимо. Так как внешних потребителей управляющего API нет, package `lti.gateway.management.v1` сохраняется, а несовместимость фиксируется в шапке файла. При появлении внешнего потребителя управляющего API создаётся `v2`.

Кодогенерация выполняется один раз в `Contracts`; сервисы не генерируют типы повторно.

### D9. Миграции и порядок выката

Схемой владеет management: миграции применяются при его старте, реплики стартуют последовательно. Flow миграции не применяет и при несовместимой схеме завершает запуск ошибкой. Все изменения схемы обязаны быть expand/contract-совместимыми, потому что flow-поды обновляются независимо: сначала добавляем новые колонки и таблицы, переводим чтение, только в следующем релизе удаляем старое.

Порядок в ArgoCD: management → flow по интеграциям.

### D10. Секреты и проверка при старте

Секреты общие для всех экземпляров и читаются из конфигурации (`ISecretStore` не меняется). Management при старте проверяет секреты всей активной конфигурации, flow — только конфигурации своей интеграции. Значения секретов по-прежнему не хранятся в БД и не попадают в ответы API. Риск: любой экземпляр flow располагает ключами всех интеграций; граница изоляции — конфигурационная, не сетевая. Ключи уже per-channel, поэтому разграничение можно ввести позже без изменения кода.

### D11. Локальная разработка и наблюдаемость

AppHost — инструмент разработки: контейнер PostgreSQL, management с двумя репликами, по два экземпляра flow на интеграцию, встроенный dashboard. Dashboard хранит телеметрию в памяти и в прод не переносится: в кластере экспорт идёт в OTel Collector. OTLP endpoint берётся из стандартных переменных окружения, которые AppHost прокидывает сам; `OtelOptions` сохраняет имя сервиса, версию, долю сэмплирования и интервал экспорта.

Прод-манифесты (Deployment, Service, Ingress на интеграцию, ConfigMap/Secret, sync waves) пишутся вручную и живут отдельно от AppHost.

### D12. Тесты

`Testcontainers.PostgreSql`: один контейнер на прогон, отдельная база или схема на тест. SQLite из тестов удаляется полностью — он не проверяет ни partial unique index, ни `SKIP LOCKED`, ни конкурентность. Тесты разделяются по сервисам; сценарии двух реплик (гонка активаций, конкурентная выборка диспетчера) выполняются на двух экземплярах в одном тесте.

## Risks / Trade-offs

| Риск | Следствие | Смягчение |
|---|---|---|
| Активация стала согласованной в конечном счёте | В окне применения новый маршрут может отвечать `404` | SLO 5 секунд, polling 2 секунды, applied-версия в состоянии |
| Одна БД на два сервиса | Связность релизов по схеме | expand/contract, единственный владелец миграций, порядок выката |
| Общие секреты | Компрометация одного пода раскрывает ключи всех интеграций | Принято осознанно; ключи per-channel, разграничение можно ввести позже |
| Изоляция только конфигурационная | Требование «bank-a не может вызвать bank-b» выполнено лишь в части настроек | Формулировка требования изменена; при необходимости добавить NetworkPolicy |
| `SYNC` входящий режим | Ответ может не дойти до инициатора при двух репликах | Спайк до реализации; при провале — reply-очередь на запрос |
| Ограничение частоты на экземпляр | Суммарная квота интеграции равна сумме квот реплик | Зафиксировано в спеке; распределённый лимитер вне объёма |
| Общая таблица сообщений | Любой участник видит очереди всех интеграций | Принято: шина — доверенная зона |
| Тесты требуют Docker | Локальный и CI-прогон зависят от контейнеров | Зафиксировать в README; альтернатива — внешний тестовый PostgreSQL |

## Открытые вопросы

1. **Жизненный цикл интеграции**: создаётся ли интеграция через управляющий API или задаётся конфигурацией деплоймента, и кто ведёт её список.
2. **Переходный период адреса очереди**: как продукты переходят со `lti.gateway.outbound` на `lti.gateway.<integration>.outbound` — одновременный релиз или временная пересылка.
3. **Спайк `SYNC`** при двух репликах на одной очереди.
4. **ServiceDefaults**: использовать Aspire `AddServiceDefaults()` или собственный набор (предпочтителен собственный — сохраняет `/health/live`, `/health/ready` и `OtelOptions`).
5. **Согласование квоты на экземпляр** с владельцами интеграций.

## Волны реализации

1. **Контракты**: `protos/` в корень, проект `Contracts`, обновление путей и проверки документации `.proto`.
2. **PostgreSQL**: провайдер EF Core, транспорт Rebus, инварианты в схеме, миграции заново, тесты на Testcontainers.
3. **Разделение сервисов**: `Core`, `Management`, `Flow`, скоуп интеграции, версия конфигурации, polling, состояние экземпляра, миграция спек и поведения.
4. **Aspire**: `AppHost` и `ServiceDefaults`, локальный контур с репликами и dashboard.
5. **Документация**: `ARCHITECTURE.md`, `README.md`, `AGENTS.md`, `openspec/config.yaml`.
