# management-api Specification

## Purpose

Управляющие операции шлюза: единый Protobuf-контракт для gRPC и REST, аутентификация по ключу API,
жизненный цикл каналов и ревизий, маршруты продуктов, чтение статуса исходящей операции и аудит
управляющих действий.

## Requirements

### Requirement: Управляющие операции требуют ключ API

Каждая управляющая операция SHALL требовать ключ API из заголовка запроса. Ключ SHALL сравниваться
за постоянное время. Отсутствие или неверное значение SHALL приводить к отказу `401`
(`Unauthenticated`) без деталей, при этом операция SHALL не выполняться. Если ключ не настроен в
конфигурации, управляющие операции SHALL отвечать `503` (`Unavailable`).

#### Scenario: Запрос без ключа

- **WHEN** управляющая операция вызывается без заголовка с ключом
- **THEN** ответ имеет статус `401` (`Unauthenticated`)
- **AND** тело ответа не содержит причины отказа и ожидаемого значения
- **AND** операция не изменяет конфигурацию

#### Scenario: Неверный ключ

- **WHEN** управляющая операция вызывается с неверным ключом
- **THEN** ответ имеет статус `401` (`Unauthenticated`)

#### Scenario: Ключ не настроен

- **WHEN** ключ API отсутствует в конфигурации окружения
- **THEN** управляющая операция отвечает `503` (`Unavailable`)
- **AND** операция не выполняется

#### Scenario: Верный ключ

- **WHEN** управляющая операция вызывается с настроенным ключом
- **THEN** операция выполняется и возвращает результат

### Requirement: Один контракт для gRPC и REST

Управляющие операции SHALL быть доступны как gRPC-вызовы и как REST-запросы через JSON transcoding,
при этом обе формы SHALL давать одинаковый результат и одинаково требовать ключ API. Ресурсы
`outbound-channels` и `inbound-channels` SHALL быть разделены в REST и gRPC.

#### Scenario: REST через transcoding

- **WHEN** выполняется `GET /v1/outbound-channels` или `GET /v1/inbound-channels` с корректным ключом
- **THEN** ответ содержит список каналов соответствующего направления в JSON
- **AND** состав данных совпадает с результатом соответствующего gRPC-вызова

#### Scenario: Одинаковые требования аутентификации

- **WHEN** `GET /v1/outbound-channels` или `GET /v1/inbound-channels` вызывается без ключа
- **THEN** ответ имеет статус `401`

### Requirement: Жизненный цикл канала доступен через API

API SHALL предоставлять независимое создание, чтение и изменение outbound- и inbound-каналов.
`CreateOutboundChannel` SHALL создавать канал с черновиком ревизии 1. `CreateInboundChannel` SHALL
требовать OpenAPI-документ и создавать канал с черновиком контракта 1. Публикация и активация
SHALL оставаться отдельными шагами. Невалидная операция SHALL возвращать полный список проблем и
SHALL не изменять активную конфигурацию.

#### Scenario: Создание outbound-канала

- **WHEN** создаётся outbound-канал `bank-a` с настройками HTTP
- **THEN** ответ содержит идентификатор канала и номер черновой ревизии
- **AND** активной ревизии у канала нет

#### Scenario: Создание inbound-канала

- **WHEN** создаётся inbound-канал `bank-a` с OpenAPI-документом
- **THEN** создаётся канал и черновик версии контракта 1
- **AND** endpoints не активны до публикации и активации

#### Scenario: Создание канала

- **WHEN** создаётся outbound-канал `bank-a` с базовым URL и настройками
- **THEN** ответ содержит идентификатор канала и номер черновой ревизии
- **AND** активной ревизии у канала нет

#### Scenario: Изменение черновика

- **WHEN** у outbound-канала изменяются настройки в черновике
- **THEN** изменения сохраняются в черновике
- **AND** активная ревизия остаётся прежней

#### Scenario: Публикация с ошибками

- **WHEN** публикуется черновик с недопустимой конфигурацией
- **THEN** ответ содержит все найденные проблемы
- **AND** активная конфигурация не меняется

#### Scenario: Активация и откат

- **WHEN** публикуется и активируется новая outbound-ревизия, затем выполняется откат
- **THEN** активной становится предыдущая опубликованная ревизия

#### Scenario: Публикация и активация

- **WHEN** черновик outbound-ревизии или inbound-контракта публикуется и активируется
- **THEN** активной становится указанная версия своего направления
- **AND** активная конфигурация другого направления не изменяется

### Requirement: Маршруты продуктов управляются через API

API SHALL предоставлять регистрацию маршрута продукта (разрешённые каналы и адреса очередей) и
чтение маршрута по идентификатору продукта.

#### Scenario: Регистрация маршрута

- **WHEN** для продукта `dpv` регистрируются канал `bank-a` и адрес `dpv.inbox`
- **THEN** повторное чтение маршрута возвращает эти значения

#### Scenario: Неизвестный продукт

- **WHEN** запрашивается маршрут незарегистрированного продукта
- **THEN** ответ имеет статус `404` (`NotFound`)

### Requirement: Статус исходящей операции доступен по идентификатору

API SHALL возвращать состояние исходящей операции по `message_id`: состояние, исход, HTTP-статус,
код ошибки и число попыток.

#### Scenario: Существующая операция

- **WHEN** запрашивается операция с известным `message_id`
- **THEN** ответ содержит состояние, исход и число попыток

#### Scenario: Неизвестная операция

- **WHEN** запрашивается операция с неизвестным `message_id`
- **THEN** ответ имеет статус `404` (`NotFound`)

### Requirement: Управляющие операции попадают в аудит

Управляющая операция, изменяющая конфигурацию, и чтение отдельного объекта — успешные и отклонённые —
SHALL фиксироваться в аудите с указанием операции, объекта и результата. Обзорные списки, то есть
методы `List*`, SHALL NOT создавать записи аудита. Значения секретов SHALL в аудит не попадать.

#### Scenario: Успешная операция

- **WHEN** канал публикует ревизию через API
- **THEN** аудит содержит запись с операцией публикации, каналом и результатом

#### Scenario: Отклонённая операция

- **WHEN** публикация отклонена из-за проблем конфигурации
- **THEN** аудит содержит запись об отказе
- **AND** в аудите нет значений секретов

#### Scenario: Чтение канала

- **WHEN** канал успешно читается через API
- **THEN** аудит содержит запись с операцией чтения, именем канала и результатом

#### Scenario: Отказ валидации настроек версии

- **WHEN** настройки версии отклонены до вызова среза (нет настроек или неизвестный тип авторизации)
- **THEN** аудит содержит запись об отказе с перечнем проблем
- **AND** значения секретов в аудите отсутствуют

#### Scenario: Обзорный список

- **WHEN** список каналов или интеграций запрашивается через управляющий API
- **THEN** новых записей в аудите не появляется
- **AND** ответ содержит запрошенный список

### Requirement: Проблемы валидации возвращаются полным списком

Ответ управляющей операции SHALL содержать все найденные проблемы за один вызов, а не первую
найденную.

#### Scenario: Несколько проблем

- **WHEN** ревизия канала публикуется с недопустимым URL и пустой политикой повторов
- **THEN** ответ содержит проблемы `base_url` и `retry_policy`

### Requirement: Проблемы несут severity

Каждый `OperationProblem` SHALL содержать `severity`: `ERROR` для отказа и `WARNING` для
предупреждения. `ContractOperationResponse` SHALL NOT иметь отдельного списка `warnings`:
предупреждения передаются в `problems` с `severity = WARNING`, а `succeeded` отражает результат
операции.

#### Scenario: Отказ

- **WHEN** управляющая команда отклонена проверкой
- **THEN** её проблемы имеют `severity = ERROR`
- **AND** `succeeded = false`

#### Scenario: Предупреждение

- **WHEN** операция выполнена, но есть замечание (например, отсутствует секрет канала)
- **THEN** `succeeded = true`
- **AND** предупреждение присутствует в `problems` с `severity = WARNING`

### Requirement: Обязательные поля команд проверяются

Management-команды SHALL проверять обязательные поля запроса до бизнес-логики. Пустое обязательное
поле SHALL давать проблему с `severity = ERROR` и `succeeded = false`. Методы чтения SHALL сохранять
текущее поведение: пустое имя канала или версии возвращает `NotFound`.

#### Scenario: Пустое имя канала

- **WHEN** команда создания, изменения, публикации, активации или отката получает пустое имя канала
- **THEN** ответ содержит проблему `severity = ERROR` с кодом поля
- **AND** `succeeded = false`
- **AND** срез не вызывается

#### Scenario: Пустое имя в чтении

- **WHEN** запрос чтения канала содержит пустое имя
- **THEN** ответ имеет статус `404` (`NotFound`)

### Requirement: Настройки версии контракта управляются через API

Управляющий API SHALL отдавать настройки версии контракта и SHALL позволять изменять их для
черновика: очередь получателя, тип авторизации с несекретными параметрами и квоту частоты.
Изменение опубликованной версии SHALL отклоняться, отсутствие версии SHALL возвращать `404`
(`NotFound`), неверный тип авторизации — проблему с кодом `auth_type`.

#### Scenario: Чтение настроек

- **WHEN** запрашивается версия контракта канала
- **THEN** ответ содержит очередь получателя, тип авторизации, имя заголовка или пользователя,
  ключ конфигурации и квоту частоты
- **AND** значение секрета в ответе отсутствует

#### Scenario: Изменение черновика

- **WHEN** для черновика задаются очередь получателя и тип авторизации `basic`
- **THEN** операция завершается успешно
- **AND** повторное чтение возвращает новые значения

#### Scenario: Изменение опубликованной версии

- **WHEN** настройки изменяются для опубликованной версии
- **THEN** ответ содержит проблему с кодом `version`, настройки не меняются

#### Scenario: Неверный тип авторизации

- **WHEN** задаётся тип авторизации вне набора `none`, `api_key`, `basic`, `client_certificate`
- **THEN** ответ содержит проблему с кодом `auth_type`

#### Scenario: Неизвестная версия

- **WHEN** запрашивается версия, которой нет у канала
- **THEN** ответ имеет статус `404` (`NotFound`)

### Requirement: Настройки операции доступны через управляющий API

Управляющий API SHALL отдавать настройки каждой операции версии контракта (`enabled` и
переопределение очереди) и SHALL позволять изменять их для версии, кроме `superseded`. Изменение
настроек активной версии SHALL применяться к работающим маршрутам без перезапуска. Неизвестная
версия или операция SHALL возвращать `404` (`NotFound`). Операции без `operationId` в документе
управляющим API не адресуются: чтобы менять их настройки, контракт должен задавать `operationId`.

#### Scenario: Чтение настроек операции

- **WHEN** запрашиваются операции версии контракта
- **THEN** каждая операция содержит `enabled` и переопределение очереди
- **AND** отсутствие переопределения выражается пустой строкой

#### Scenario: Изменение настроек опубликованной версии

- **WHEN** для операции опубликованной версии задаются `enabled = false` и собственная очередь
- **THEN** операция завершается успешно
- **AND** повторное чтение возвращает новые значения

#### Scenario: Изменение настроек активной операции

- **WHEN** для операции активной версии задаётся `enabled = false`
- **THEN** операция завершается успешно
- **AND** последующий вызов этой операции получает `404` без перезапуска приложения

#### Scenario: Переопределение квоты

- **WHEN** запрашивается переопределение квоты на операции
- **THEN** настройка не поддерживается
- **AND** применяется квота версии контракта или общая квота приложения

#### Scenario: Отменённая версия

- **WHEN** настройки операции изменяются для версии `superseded`
- **THEN** ответ содержит проблему `version`
- **AND** настройки не меняются

#### Scenario: Неизвестная операция

- **WHEN** запрашивается изменение операции, которой нет в версии
- **THEN** ответ имеет статус `404` (`NotFound`)

#### Scenario: Операция без operationId

- **WHEN** операция документа объявлена без `operationId`
- **THEN** её настройки недоступны через управляющий API
- **AND** запрос изменения возвращает `404` (`NotFound`)

#### Scenario: Изменение попадает в аудит

- **WHEN** настройки операции изменяются через управляющий API
- **THEN** аудит содержит операцию, канал, версию, `operationId` и результат
- **AND** значения секретов в аудите отсутствуют

### Requirement: Состояние канала доступно через управляющий API

Управляющий API SHALL возвращать состояние канала: наличие активной ревизии и её номер, признак
настроенного секрета и имя ключа конфигурации без значения, срок действия клиентского сертификата,
последние ошибки обмена и время проверки. Значение секрета, тела сообщений и авторизационные
заголовки SHALL в ответ не попадать. Неизвестный канал SHALL возвращать `404` (`NotFound`).

#### Scenario: Канал с активной ревизией

- **WHEN** запрашивается состояние канала с активной ревизией
- **THEN** ответ содержит номер активной ревизии, состояние `ACTIVE`, признак секрета, срок
  сертификата (если тип авторизации `client_certificate`) и последние ошибки

#### Scenario: Секрет не настроен

- **WHEN** активная ревизия требует секрет, а значение по ключу конфигурации отсутствует
- **THEN** признак настроенного секрета равен `false`
- **AND** ответ содержит имя ключа конфигурации без значения

#### Scenario: Канал без активной ревизии

- **WHEN** у канала нет активной ревизии
- **THEN** ответ имеет статус `200` и состояние `NO_ACTIVE_REVISION`
- **AND** номер активной ревизии равен `0`

#### Scenario: Неизвестный канал

- **WHEN** запрашивается состояние незарегистрированного канала
- **THEN** ответ имеет статус `404` (`NotFound`)

#### Scenario: Истёкший клиентский сертификат

- **WHEN** активная ревизия использует `client_certificate`, а срок действия сертификата истёк
- **THEN** признак настроенного секрета равен `false`
- **AND** срок действия сертификата присутствует в ответе для диагностики
- **AND** значение материала и пароля отсутствует

#### Scenario: Последние ошибки

- **WHEN** в журналах есть ошибки обмена по каналу
- **THEN** ответ содержит не более пяти последних ошибок по каждому направлению
- **AND** каждая ошибка содержит время, направление, код ошибки и HTTP-статус для исходящих
- **AND** тела сообщений и заголовки авторизации отсутствуют

#### Scenario: Чтение фиксируется в аудите

- **WHEN** состояние канала запрашивается через управляющий API
- **THEN** аудит содержит операцию чтения состояния с каналом и результатом
- **AND** значения секретов в аудите отсутствуют

### Requirement: Отсутствие канала возвращает NotFound

Управляющие операции, адресованные по имени канала, SHALL возвращать `404` (`NotFound`), если канал
не зарегистрирован, и SHALL фиксировать отказ в аудите. Это относится к чтению канала и к изменяющим
операциям над каналом.

#### Scenario: Чтение неизвестного канала

- **WHEN** запрашивается канал, которого нет
- **THEN** ответ имеет статус `404` (`NotFound`)
- **AND** аудит содержит отклонённую операцию чтения с именем канала

#### Scenario: Изменение неизвестного канала

- **WHEN** изменяется черновик, публикуется, активируется или откатывается ревизия неизвестного канала
- **THEN** ответ имеет статус `404` (`NotFound`)
- **AND** аудит содержит отклонённую операцию с именем канала

### Requirement: Направления каналов имеют независимые ресурсы

Management API SHALL адресовать outbound- и inbound-каналы через разные ресурсы. Одинаковые имена
в разных направлениях SHALL быть допустимы. `BOTH` SHALL NOT поддерживаться.

#### Scenario: Одинаковое имя в двух направлениях

- **WHEN** существуют `OutboundChannel bank-a` и `InboundChannel bank-a`
- **THEN** обе записи доступны по своим direction-first путям
- **AND** изменение одной не изменяет другую

#### Scenario: Двунаправленный канал

- **WHEN** клиент пытается создать канал с направлением `BOTH`
- **THEN** запрос отклоняется как некорректный

### Requirement: Inbound-канал создаётся с OpenAPI-документом

`CreateInboundChannel` SHALL принимать имя, OpenAPI-документ и необязательные `response_mode` и
`inbound_response_timeout_ms`. При отсутствии режим SHALL быть `ASYNC`, timeout SHALL быть `30000`.
Канал SHALL создаваться с черновиком контракта 1 и без активных endpoints.

#### Scenario: Параметры по умолчанию

- **WHEN** создаётся inbound-канал без режима и timeout
- **THEN** канал получает `ASYNC` и timeout `30000`
- **AND** создаётся черновик контракта 1

#### Scenario: Явные параметры

- **WHEN** создаётся inbound-канал с `SYNC` и timeout `7200000`
- **THEN** параметры сохраняются в канале
- **AND** черновик контракта создаётся без активации endpoints

### Requirement: Настройки inbound-канала изменяются через API

API SHALL предоставлять изменение `response_mode` и `inbound_response_timeout_ms` через отдельную
операцию с аудитом. Изменение SHALL применяться к новым запросам; уже ожидающие запросы SHALL
использовать значение, зафиксированное при старте ожидания.

#### Scenario: Изменение режима

- **WHEN** `response_mode` меняется с `ASYNC` на `SYNC`
- **THEN** новые запросы канала ожидают `InboundResponse`
- **AND** ранее начатые запросы не меняют режим

#### Scenario: Изменение timeout

- **WHEN** timeout увеличивается или уменьшается
- **THEN** новое значение применяется к последующим запросам
- **AND** изменение фиксируется в аудите

### Requirement: Маршруты продуктов используют только outbound-каналы

`RegisterProductRoute` SHALL принимать имена только зарегистрированных outbound-каналов. Inbound-канал
SHALL NOT быть допустимым значением маршрута продукта.

#### Scenario: Outbound-канал в маршруте

- **WHEN** продукту разрешается существующий outbound-канал
- **THEN** маршрут сохраняется
- **AND** продукт может отправлять через него `OutboundRequest`

#### Scenario: Inbound-канал в маршруте

- **WHEN** в маршруте продукта указывается inbound-канал
- **THEN** регистрация отклоняется
- **AND** существующий маршрут не меняется

### Requirement: Контракты адресуются inbound-каналом

Операции загрузки, публикации, активации и чтения версий контракта SHALL адресоваться через
`/v1/inbound-channels/{channel_name}/contracts`. Outbound-канал SHALL NOT принимать эти операции.

#### Scenario: Контракт inbound-канала

- **WHEN** публикуется версия контракта существующего inbound-канала
- **THEN** операция выполняется в пространстве этого канала
- **AND** outbound-канал недоступен для этой операции

#### Scenario: Неизвестный inbound-канал

- **WHEN** контракт адресован по имени неизвестного inbound-канала
- **THEN** ответ имеет статус `404`
- **AND** контракт не создаётся и не изменяется

### Requirement: REST-контракт управляющего API публикуется как OpenAPI-документ

Сервис управления SHALL публиковать OpenAPI 3.0-документ своего REST-контракта по
`/openapi/management.json` и SHALL предоставлять Swagger UI по `/swagger`. Документ SHALL строиться из
того же Protobuf-контракта, что и transcoding-маршруты: пути и HTTP-методы SHALL соответствовать
аннотациям `google.api.http`, схемы запросов и ответов — сообщениям, описания — комментариям
`management_api.proto`. Отдельный источник истины для документа SHALL NOT вводиться. Документ и UI
SHALL быть доступны без ключа API и SHALL NOT содержать значения секретов.

#### Scenario: Документ содержит все REST-маршруты

- **WHEN** запрашивается `/openapi/management.json`
- **THEN** документ содержит операцию для каждого rpc, у которого задана аннотация `google.api.http`
- **AND** путь и HTTP-метод каждой операции совпадают с аннотацией

#### Scenario: Изменение контракта отражается без правки кода

- **WHEN** в `management_api.proto` добавляется rpc с новой аннотацией `google.api.http`
- **THEN** после пересборки и запуска сервиса операция появляется в документе
- **AND** отдельный файл документа или описание маршрута в коде не правятся

#### Scenario: Схемы и описания

- **WHEN** операция документа описывает запрос и ответ
- **THEN** тело запроса и ответа ссылаются на схемы соответствующих сообщений
- **AND** описания операции и полей взяты из комментариев `.proto`

#### Scenario: Параметры пути

- **WHEN** путь операции содержит переменные вида `{channel_name}`
- **THEN** каждая переменная описана параметром `in: path` с `required: true`
- **AND** тип параметра соответствует типу поля сообщения запроса

#### Scenario: Доступ без ключа

- **WHEN** документ или Swagger UI запрашивается без ключа API
- **THEN** ответ успешен
- **AND** управляющие операции, вызванные из UI, по-прежнему требуют ключ API

### Requirement: Список интеграций доступен через управляющий API

Управляющий API SHALL предоставлять перечисление интеграций: gRPC-метод `ListIntegrations` и REST
`GET /v1/integrations` через JSON transcoding. Ответ SHALL содержать все записи интеграций,
упорядоченные по идентификатору, с идентификатором, версией действующей конфигурации и временем
появления записи. Метод SHALL NOT адресоваться интеграцией: scope-поля в запросе нет. Пустой список
SHALL быть успешным результатом. Обе формы доступа SHALL давать одинаковый результат.

#### Scenario: Настроенные интеграции

- **WHEN** в интеграциях `bank-a` и `bank-b` созданы каналы
- **THEN** ответ содержит записи `bank-a` и `bank-b` в порядке идентификаторов
- **AND** каждая запись содержит версию действующей конфигурации и время появления записи

#### Scenario: Нет настроенных интеграций

- **WHEN** ни для одной интеграции не выполнялось изменяющих операций
- **THEN** ответ успешен
- **AND** список интеграций пуст

#### Scenario: Интеграция по умолчанию

- **WHEN** настройка выполнялась без явной адресации интеграции
- **THEN** в списке присутствует интеграция `default`

#### Scenario: Одинаковый результат по gRPC и REST

- **WHEN** список запрашивается через `GET /v1/integrations` и через gRPC `ListIntegrations`
- **THEN** состав данных совпадает
- **AND** запрос без ключа API отклоняется
