# LtiIntegrationGateway

Шлюз интеграции продуктов LTI с внешними системами: принимает и передаёт данные через
Rebus, выполняет исходящие HTTP-вызовы по конфигурации каналов, валидирует входящие запросы
по OpenAPI.

Архитектура и требования: [`docs/adr/0001-integration-gateway.md`](docs/adr/0001-integration-gateway.md).
Планирование изменений ведётся в OpenSpec (`openspec/`).

## Требования

- .NET SDK 10.0
- `global.json` включает новый режим `dotnet test` для Microsoft.Testing.Platform (TUnit),
  иначе `dotnet test` на .NET 10 SDK не сможет запустить тесты MTP

## Обязательная настройка

Приложение не стартует без строки подключения к хранилищу:

```json
{
  "ConnectionStrings": {
    "Gateway": "Data Source=gateway.db"
  }
}
```

Ключ `ConnectionStrings:Gateway` задаётся в `appsettings.json`, в
`appsettings.Development.json` или через переменную окружения
`ConnectionStrings__Gateway`. Если ключ отсутствует или пуст, запуск завершается ошибкой с
именем ключа — это ожидаемое поведение, а не дефект.

## Команды

```bash
# восстановление и сборка
dotnet build LtiIntegrationGateway.slnx

# тесты (TUnit, Microsoft.Testing.Platform)
dotnet test LtiIntegrationGateway.slnx

# запуск приложения
dotnet run --project src/LtiIntegrationGateway
```

## Контракты

Контракт обмена сообщениями между продуктами и шлюзом — один файл:
`src/LtiIntegrationGateway/Protos/v1/integration_messages.proto`
(`package lti.gateway.messages.v1`). Потребитель забирает `.proto` и генерирует типы
самостоятельно; пакет контрактов не публикуется.

- C#-типы генерируются при сборке (`dotnet build`), вручную не редактируются;
- профиль кодирования на проводе (ProtoJSON, camelCase, `bytes` → base64, неизвестные поля
  игнорируются, `rbs2-msg-type` = полное имя сообщения) описан в шапке `.proto` и является
  обязательным для всех потребителей;
- обязательные поля `OutboundRequest` проверяются `Contracts/MessageContractValidator`.

## Шина

Rebus подключён через `Infrastructure/Rebus/RebusConfigurationExtensions.AddGatewayRebus()`
(вызов из `Program.cs`):

- входная очередь шлюза — `lti.gateway.outbound`;
- error-queue — `lti.gateway.error`: сообщение, не обработанное после всех попыток, попадает туда
  (ADR §10.2, решение 28); число попыток и кулдаун остаются значениями по умолчанию Rebus;
- транспорт — in-memory (стартовый вариант, ADR §10.1);
- сериализатор — собственный `Infrastructure/Rebus/ProtobufSerializer`, а не стандартный
  JSON-сериализатор Rebus: тело — ProtoJSON по профилю из `.proto`, тип определяется заголовком
  `rbs2-msg-type`;
- реестр типов — `Infrastructure/Rebus/ProtobufMessageRegistry`, покрывает все сообщения
  контракта `lti.gateway.messages.v1`.

Имена очередей задаёт `Infrastructure/Rebus/QueueNames`. Очередь продукта не конфигурируется:
она вычисляется из `product_id` как `<product_id>.inbox` (например, `dpv.inbox`) и используется
для `OutboundResult` и `InboundMessage` (ADR §10.2).

Ограничение текущего этапа: маршрутизация между продуктами не настроена; контроль доступа
к очередям на стороне брокера — требование к промышленному транспорту (ADR §20).

## Исходящий контур

Обработчик `Features/Outbound/OutboundRequestHandler` подписан на `OutboundRequest` в очереди
`lti.gateway.outbound` и выполняет шаги в фиксированном порядке:

1. обязательные поля запроса (`Contracts/MessageContractValidator`);
2. `product_id` и заголовок `rbs2-sender-address` по конфигурации `ProductRoutes`
   (`Features/ProductRoutes`), включая разрешённость канала продукту: адрес отправителя должен
   совпадать с вычисленным `<product_id>.inbox`;
3. адрес доставки результата (`rbs2-return-address`) — только вычисленный `<product_id>.inbox`;
4. идемпотентность по `message_id` (уникальный индекс `OutboundOperations.MessageId`);
5. активная ревизия канала, разрешённый метод и путь (структурные запреты + шаблоны);
6. авторизация из конфигурации (`none`, `bearer`, `api_key` — заголовок или query-параметр,
   `basic`, `client_certificate` — клиентский сертификат в TLS-рукопожатии);
7. HTTP-вызов через обработчик пула по ключу `(base_url, auth_type, отпечаток сертификата)` с
   повторами по политике ревизии (`AllowAutoRedirect = false`, TLS 1.2+).

Повторный `OutboundRequest` с завершённым `message_id` не вызывает внешнюю систему: результат
восстанавливается из операции и журнала (`Features/Outbound/StoredOutboundResultFactory`) и
отправляется на адрес из **текущего** сообщения. Тело ответа, `Content-Type`, HTTP-статус, исход,
код и текст ошибки, число попыток и `correlation_id` совпадают с первым результатом (ADR §8.10);
запрос с чужим `product_id` отклоняется кодом `PRODUCT_NOT_ALLOWED`.

Проверка владения `product_id` выполняется до выдачи сохранённого результата, а для завершённой
операции активная ревизия канала, метод, путь и авторизация повторно не проверяются: состояние
операции важнее текущей конфигурации канала. Отказ не переписывает состояние чужой или завершённой
операции и не меняет признак доставки сохранённого результата: чужая `Pending`-запись остаётся
в очереди диспетчера и доставляется владельцу.

Исходы и коды в `OutboundResult`:

| `outcome`         | коды                                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| `GATEWAY_REFUSED` | `PRODUCT_NOT_ALLOWED`, `CHANNEL_NOT_ALLOWED`, `CHANNEL_NOT_ACTIVE`, `METHOD_NOT_ALLOWED`, `PATH_NOT_ALLOWED`, `SECRET_NOT_CONFIGURED`, `AUTH_TYPE_UNSUPPORTED` |
| `TRANSPORT_ERROR` | `TIMEOUT`, `CONNECTION_FAILED`, `TLS_FAILED`, `RETRIES_EXHAUSTED`                                        |
| `HTTP_RESPONSE`   | статус и тело ответа внешней системы; ошибки `4xx`/`5xx` не приводят к повтору на уровне шины            |

Повторы задаются политикой канала (`ChannelRevision.RetryPolicy`): правила `http_status_in` и
`transport_error`, массив задержек в миллисекундах, учёт `Retry-After` и общего предела
`OverallCapMs`; таймаут — на попытку. `POST` и `PATCH` повторяются только при непустом
`idempotency_key`. Отсутствующее значение секрета — отказ `SECRET_NOT_CONFIGURED`; для
`client_certificate` тем же кодом завершается отсутствие или непригодность материала сертификата.
`AUTH_TYPE_UNSUPPORTED` возвращается только для типа авторизации вне набора (повреждённая
конфигурация).

### Клиентский сертификат канала

Канал с типом авторизации `client_certificate` предъявляет клиентский сертификат в
TLS-рукопожатии. Материал задаётся ключом конфигурации ревизии (`config_key`):

| Ключ конфигурации | Значение |
|---|---|
| `<config_key>` | путь к PFX-файлу либо PFX в base64 |
| `<config_key>:Password` | пароль PFX; пустое значение допустимо для незащищённого файла |

Правила:

- значение трактуется как путь к файлу, если такой файл существует, иначе — как PFX в base64;
- PFX загружается с `X509KeyStorageFlags.EphemeralKeySet`; проверяются наличие приватного ключа и
  срок действия — истёкший или ещё не вступивший в силу сертификат даёт `SECRET_NOT_CONFIGURED`
  до HTTP-вызова;
- материал кэшируется по ключу конфигурации на время жизни процесса: PFX разбирается один раз,
  экземпляр сертификата общий для всех вызовов канала и освобождается при остановке приложения;
- значения материала и пароля не попадают в базу, `OutboundResult`, журнал, логи и ответы API;
- смена материала (файла, base64 или пароля) вступает в силу только после перезапуска приложения
  (ADR §7.4).

HTTP-обработчики пулируются по ключу `(base_url, auth_type, SHA-256 отпечаток сертификата)`:
каналы с одинаковым ключом переиспользуют соединения, каналы с разными сертификатами не
смешиваются. Обработчик создаётся с `AllowAutoRedirect = false`, TLS 1.2/1.3 и
`PooledConnectionLifetime` 5 минут; запись пула пересоздаётся через 15 минут, а прежний обработчик
освобождается после завершения начатых вызовов. Вытеснение записей при большом числе ключей не
реализовано и зафиксировано как открытый вопрос.

Состояние операции и журнал:

- `OutboundOperations` — состояние (`Accepted`/`InProgress`/`Completed`), исход, число попыток,
  адрес доставки и `correlation_id` первого запроса; `MessageId` уникален, повторный запрос не
  вызывает внешнюю систему;
- `OutboundMessageLogs` — тела запроса и ответа, статус, исход, `Content-Type` и текст ошибки,
  адрес доставки результата, номер активной ревизии канала и `DeliveryStatus` (`Pending` → `Sent`
  после отправки результата в очередь продукта); выборка недоставленных записей идёт по индексу
  `(DeliveryStatus, CreatedAtUnixMs)`.

Запись операции и журнала (включая адрес доставки, `correlation_id`, текст ошибки, номер ревизии
канала и `CreatedAtUnixMs`) фиксируется одной транзакцией до отправки результата; значения секретов
не попадают ни в журнал, ни в результат.

### Диспетчер доставки результатов

Результат фиксируется в журнале со статусом `Pending` до попытки отправки, поэтому сбой `Send` не
теряет результат: его повторно отправляет фоновая служба
`Features/Outbound/OutboundResultDispatcher` (`BackgroundService`, ADR §8.9).

- служба периодически читает `Pending`-записи журнала, восстанавливает результат через
  `StoredOutboundResultFactory` и отправляет его на сохранённый адрес доставки;
- выборка выполняется в SQL по индексу `(DeliveryStatus, CreatedAtUnixMs)` и упорядочена по
  `CreatedAtUnixMs`; записи без адреса доставки и без операции в неё не попадают, поэтому не
  занимают пачку и не задерживают доставляемые результаты (остаются в журнале);
- отправка и фиксация статуса разделены: сбой `Send` оставляет запись `Pending` до следующего цикла
  (`Warning` «отправка не удалась»); сбой фиксации после успешной отправки даёт `Error` «результат
  отправлен, статус не зафиксирован — возможен дубль», запись перечитывается из БД и будет отправлена
  повторно;
- в лог попадают только `messageId`, канал и причина; тела и значения секретов не логируются.

| Ключ конфигурации | Значение по умолчанию | Смысл |
|---|---|---|
| `Outbound:DeliveryDispatcher:Enabled` | `true` | запуск фоновой службы |
| `Outbound:DeliveryDispatcher:IntervalSeconds` | `15` | пауза между циклами, не меньше 1 |
| `Outbound:DeliveryDispatcher:BatchSize` | `50` | записей за цикл, от 1 до 500 |

Значения вне диапазона останавливают запуск приложения. В тестовом хосте
(`GatewayWebApplicationFactory`) служба выключена по умолчанию, тесты вызывают `DispatchPendingAsync`
напрямую.

Гарантия доставки — «минимум один раз»: `Send` и смена статуса не объединены транзакцией, поэтому
падение между ними даёт дубль, но не потерю. Дубли допустимы, продукт дедуплицирует результат по
`message_id`. Распределённой блокировки нет: служба рассчитана на один экземпляр приложения
(ADR §12, §20 — открытый вопрос).

Ограничения:

- записи журнала, созданные до миграции `AddOutboundResultDispatcher`, получают пустой адрес доставки
  и диспетчером не доставляются: они не участвуют в выборке и остаются в журнале для аудита;
- на in-memory-транспорте журнал переживает перезапуск процесса, но получатель очереди — нет:
  запись может быть помечена `Sent`, хотя продукт сообщение не получил (ADR §10.1). Полная гарантия
  появляется только с промышленным транспортом.

Не реализовано на этом этапе: OAuth2 client credentials, управляющий API маршрутов продуктов (срезы
вызываются из кода и тестов), вытеснение обработчиков из пула.

## Входящий контур

Приём входящих вызовов реализован в `Infrastructure/Routing`, `Infrastructure/OpenApi` и
`Features/Inbound`:

- `InboundRouteCatalog` — активные наборы маршрутов по ключу ревизии; снапшот активных маршрутов
  неизменяем, при изменении отменяется токен изменения;
- `InboundRouteSetValidator` — проверка набора до активации: поддерживаемые методы
  (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`), разбор шаблона, дубликаты «метод + шаблон» внутри набора
  и конфликты с активными наборами; при проблемах активация не меняет состояние;
- `InboundEndpointDataSource` — публикует маршруты как настоящие endpoint'ы ASP.NET Core
  с метаданными канала, ревизии, авторизации, квоты и политики ограничения частоты; источник
  добавляется в `IEndpointRouteBuilder.DataSources` (регистрации в DI недостаточно);
- `InboundRequestHandler` — принимает вызов, проверяет запрос, создаёт `InboundMessage` и передаёт
  его в очередь получателя через `IInboundMessagePublisher`;
- `InboundRequestAuthenticator` — `none`, `api_key`, `basic`, `client_certificate`;
- `InboundSchemaCache` — схемы тела, скомпилированные один раз на ревизию (`NJsonSchema` 11.6.1);
- `InboundMessageLogWriter` — журнал `InboundMessageLog`.

Порядок проверок и коды ответов (ADR §9.6):

| Проверка | Ответ |
| --- | --- |
| query-параметров больше 64 | `400` |
| тело непустое, `Content-Type` не указан или не объявлен схемой | `415` |
| тело непустое, схема тела не объявлена | `400` |
| секрет маршрута не настроен в конфигурации | `503` |
| аутентификация не пройдена (тело ответа пустое) | `401` |
| тело не разбирается как JSON или глубина JSON больше 64 | `400` |
| тело не соответствует схеме операции | `422` |
| сообщение передано в очередь получателя | `202` |
| передача не удалась | `503` |

Настройки приёма задаются на версии контракта
(`PATCH /v1/channels/{name}/contracts/{v}/settings`): `recipient_queue`, `auth_type`
(`none`, `api_key`, `basic`, `client_certificate`), `config_key`, `header_name`, `user_name`,
`rate_limit_permit`, `rate_limit_window_seconds`. Значения секретов хранятся только в конфигурации
(`Channels__...` или переменные окружения) и не попадают ни в базу, ни в журнал, ни в ответы.

Настройки операции (`ContractOperations`) переопределяют настройки версии: `Enabled` (по умолчанию
`true`), `RecipientQueue`, `RateLimitPermit`, `RateLimitWindowSeconds`
(`PATCH /v1/channels/{name}/contracts/{v}/operations/{operationId}`, миграция
`AddContractOperationSettings`). Операции извлекаются из документа при публикации, поэтому настройки
задаются для опубликованной версии; для черновика запрос возвращает `404`. Действующие значения
вычисляются один раз при построении набора маршрутов, поэтому приём не обращается к базе:

- очередь — переопределение операции, иначе очередь версии;
- квота и окно — операция, иначе версия, иначе `Inbound:RateLimit:*`;
- авторизация операцией не переопределяется и всегда берётся из версии.

Отключённая операция остаётся в наборе (конфликты «метод + шаблон» проверяются для всех операций),
но обслуживается `InboundDisabledOperationHandler`: тело не читается, аутентификация не выполняется,
в `ManagementAuditEntries` пишется `InboundOperationDisabled` с каналом, методом и фактическим
путём, ответ — `404`. Изменение настроек активной версии перерегистрирует набор маршрутов без
перезапуска; при отказе каталога действует прежний набор, база не меняется.

Схемы тела извлекаются при публикации: локальные `$ref` разворачиваются (глубина до 32, цикл —
отказ публикации), поэтому сохранённая схема самодостаточна. Квота частоты берётся из действующих
настроек операции, при их отсутствии — из настроек версии, затем из `Inbound:RateLimit:PermitLimit`
и `Inbound:RateLimit:WindowSeconds`; ключ ограничения — канал; превышение — `429`.

Журнал: каждый принятый и каждый отклонённый вызов пишется в `InboundMessageLogs` (тело, метод,
фактический путь, шаблон, `operationId`, query-параметры, статус `pending → sent | failed`, код
ошибки, ревизия конфигурации, время получения). Запись `pending` создаётся до `Send`, поэтому сбой
передачи виден в журнале.

Не реализовано: HMAC-подпись, дедупликация входящих
вызовов, пул HTTP-обработчиков для `client_certificate`, фоновый диспетчер результатов.


## Конфигурация каналов

Модель канала хранится в `Infrastructure/Persistence/Entities`:

- `Channel` — имя канала (уникальное);
- `ChannelRevision` — набор настроек: базовый URL, тип авторизации и ключ конфигурации,
  допустимые методы и шаблоны путей, политика повторов, таймауты;
- `ChannelAllowedMethod`, `ChannelAllowedPath` — разрешённые методы и шаблоны путей ревизии;
- `ChannelAuditEntry` — аудит изменений конфигурации.

Жизненный цикл ревизии: `Draft` → `Published` → `Active` → `Superseded`. Опубликованная
ревизия неизменяема, изменение настроек — только через новую ревизию; откат активирует
предыдущую. Срезы жизненного цикла находятся в `Features/Channels`.

Проверки перед публикацией: базовый URL — абсолютный `https` без учётных данных, методы — из
фиксированного набора, шаблоны путей — по правилам ADR §8.7, политика повторов — 1..5 задержек
на правило. Отклонённая публикация возвращает список причин и не меняет активную ревизию.

Значения секретов в базе отсутствуют: хранятся только тип авторизации, ключ конфигурации и
несекретные параметры; сами значения берутся из переменных окружения. Для `client_certificate`
по ключу конфигурации задаётся путь к PFX или PFX в base64, а пароль — по ключу
`<config_key>:Password` (см. «Исходящий контур»).

Миграции EF Core применяются при старте приложения (`Database.Migrate()`). Новая миграция:

```bash
dotnet ef migrations add <Name> --project src/LtiIntegrationGateway --output-dir Infrastructure/Persistence/Migrations
```

Управляющий API каналов опубликован в `ManagementService`; срезы также вызываются из кода и тестов.

## Управляющий API

Управляющие операции публикуются из Protobuf-контракта `lti.gateway.management.v1`
(`Protos/v1/management_api.proto`): один сервис `ManagementService`, доступный как gRPC и как REST
через JSON transcoding. Реализация — `Features/Management`, доменные правила остаются в срезах
`Features/Channels`, `Features/ProductRoutes`, `Features/Contracts`.

Аутентификация: заголовок `X-Management-Api-Key` (имя настраивается), значение — переменная
окружения `Management__ApiKey`. Пустой ключ в конфигурации означает `503` для всего управляющего API;
отсутствие или несовпадение ключа — `401` без деталей (для gRPC — `Unauthenticated`). Сравнение
выполняется за постоянное время.

Основные операции (полный перечень — в ADR §15.2):

| REST | Назначение |
| --- | --- |
| `GET /v1/channels` | список каналов |
| `POST /v1/channels` | создание канала с черновиком |
| `PATCH /v1/channels/{name}/draft` | изменение черновика |
| `POST /v1/channels/{name}/revisions/{n}/publish` | публикация ревизии |
| `POST /v1/channels/{name}/revisions/{n}/activate` | активация ревизии |
| `POST /v1/channels/{name}/rollback` | откат |
| `PUT /v1/products/{id}/route` | маршрут продукта |
| `POST /v1/channels/{name}/contracts` | загрузка OpenAPI-документа |
| `POST /v1/channels/{name}/contracts/{v}/publish` | публикация версии контракта |
| `POST /v1/channels/{name}/contracts/{v}/activate` | активация версии и регистрация маршрутов |
| `GET /v1/channels/{name}/contracts/{v}/operations` | операции версии контракта |
| `GET /v1/channels/{name}/contracts/{v}` | версия контракта с настройками приёма |
| `PATCH /v1/channels/{name}/contracts/{v}/settings` | настройки приёма черновика |
| `PATCH /v1/channels/{name}/contracts/{v}/operations/{operationId}` | настройки операции: `enabled`, очередь, квота |
| `GET /v1/channels/{name}/health` | состояние канала: секрет, срок сертификата, последние ошибки |
| `GET /v1/operations/{messageId}` | статус исходящей операции |

Маршрут продукта (`PUT /v1/products/{id}/route`) принимает пустой список `allowed_queue_addresses`
(сохраняется вычисленный `<product_id>.inbox`) или адрес, равный вычисленному; любой другой адрес
отклоняется проблемой `address`, существующий маршрут при этом не меняется. Чтение маршрута
возвращает вычисленный адрес. Записи с произвольными адресами не мигрируются, но при проверке
`rbs2-sender-address` и `rbs2-return-address` список адресов маршрута не используется.

Контракты: `Infrastructure/OpenApi` читает документ (`Microsoft.OpenApi` 3.11.0) и проверяет его
fail-closed — принимается OpenAPI 3.0, Swagger 2.0 конвертируется (факт фиксируется в аудите),
OpenAPI 3.1 отклоняется; запрещённые конструкции, внешние `$ref` и поля рядом с `$ref` дают отказ
со списком проблем, неизвестный `format` — предупреждение. При публикации извлекаются схемы тела
операций; публикация без очереди получателя в настройках версии отклоняется с кодом `queue`
(ADR §15.2) — даже если все операции отключены и даже при переопределении очереди на операции, —
а очередь версии должна иметь формат `<product_id>.inbox` (ADR §10.2), иначе публикация также
отклоняется с кодом `queue` и операции не создаются. Дополнительно проверяется действующая очередь
каждой включённой операции, а настройки операций
переносятся из предыдущей версии канала по `operationId`, при его отсутствии хотя бы у одной из
сравниваемых операций — по совпадению метода и шаблона (изменённый `operationId` при том же маршруте
считается новой операцией: применяются значения по умолчанию).
Активация версии регистрирует её маршруты в каталоге входящих маршрутов, собирает схемы в кэш и
снимает маршруты предыдущей версии.

Аудит: каждая управляющая операция (включая отклонённые и чтение) пишется в
`ManagementAuditEntries` с операцией, объектом и результатом; значения секретов не сохраняются.
Изменение настроек операции пишется как `UpdateContractOperationSettings`, вызов отключённой
операции — как `InboundOperationDisabled`.

Состояние канала (`GET /v1/channels/{name}/health`) возвращает имя канала, состояние `ACTIVE` или
`NO_ACTIVE_REVISION`, номер активной ревизии (`0`, если её нет), признак настроенного секрета
(`secretConfigured`), имя ключа конфигурации без значения (`secretConfigKey`), срок действия
клиентского сертификата (`certificateExpiresAt`, только для `client_certificate`) и время проверки
(`checkedAt`). Секрет проверяется по типу авторизации активной ревизии: `none` — секрет не требуется,
`bearer`/`api_key`/`basic` — значение по ключу должно присутствовать, `client_certificate` — материал
должен загружаться и быть действительным. Срок действия сертификата возвращается и для истёкшего или
ещё не вступившего в силу материала (диагностика через `IChannelCertificateStore.GetInfo`), но тогда
`secretConfigured = false`. Отсутствие секрета не является ошибкой вызова:
это диагностическое состояние в ответе; неизвестный канал — `404` (`NotFound`).

Последние ошибки (`errors`) — не более пяти записей на направление: SQL-выборка берёт 64 последние
записи каждого журнала с непустым кодом ошибки (`ORDER BY CreatedAtUnixMs DESC` для
`OutboundMessageLog`, `ORDER BY ReceivedAtUnixMs DESC` для `InboundMessageLog`), затем объединение двух
направлений сортируется в памяти и от каждого направления остаётся пять самых свежих. Оба журнала
читаются по индексу «канал + время» (`(ChannelName, CreatedAtUnixMs)`, `(ChannelName, ReceivedAtUnixMs)`):
сортировка по `DateTimeOffset` в SQL не выполняется — SQLite её не поддерживает. В ответ попадают только
время, направление (`outbound`/`inbound`), код ошибки, HTTP-статус (для исходящих) и исход (для
исходящих); тела сообщений, заголовки и тексты ошибок не возвращаются.

Не реализовано: персональная идентичность администратора (JWT/IdP).

Ограничения управляющего API для настроек операции:

- операция без `operationId` в документе не адресуется — запрос изменения возвращает `404`;
- снять переопределение квоты операции через API нельзя: переданное значение должно быть
  положительным, иначе проблема `rate_limit` (переопределение очереди снимается пустой строкой).
