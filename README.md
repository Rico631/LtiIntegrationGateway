# LtiIntegrationGateway

`LtiIntegrationGateway` — самостоятельное приложение для интеграции продуктов LTI с внешними системами. Шлюз принимает входящие HTTP-вызовы, проверяет их по OpenAPI-контрактам, выполняет исходящие HTTP-запросы по конфигурации каналов и передаёт бизнес-данные и результаты продуктам через Rebus.

Шлюз отвечает за транспорт, каналы, аутентификацию, валидацию входящих контрактов, повторные попытки, сохранение результатов и аудит. Бизнес-смысл интеграции, формирование исходящих запросов и интерпретация ответов остаются ответственностью продуктов.

## Возможности

- **Исходящие интеграции:** продукт отправляет `OutboundRequest` через Rebus; шлюз выбирает канал, формирует HTTP-запрос, вызывает внешнюю систему и передаёт `OutboundResult` обратно продукту.
- **Входящие интеграции:** внешняя система вызывает опубликованный HTTP endpoint; шлюз находит операцию OpenAPI, проверяет запрос и передаёт `InboundMessage` целевому продукту через Rebus.
- **Управление:** каналы, маршруты продуктов, версии OpenAPI-контрактов и настройки операций управляются через gRPC API с REST-доступом посредством JSON transcoding.
- **Надёжность и аудит:** исходящие операции и сообщения журналируются; недоставленные результаты повторно отправляются фоновым диспетчером. Управляющие операции также записываются в аудит.
- **Наблюдаемость:** OpenTelemetry traces и metrics экспортируются по OTLP.

Продукты передают бизнес-данные шлюзу и получают результаты только через Rebus. Управляющий REST/gRPC API не предназначен для выполнения бизнес-интеграционных вызовов.

## Требования

- .NET SDK 10.0.
- `global.json` настроен на использование Microsoft.Testing.Platform. Это необходимо для запуска тестов TUnit через `dotnet test` на .NET 10 SDK.
- Docker для локального запуска через Aspire и для тестов: PostgreSQL поднимается контейнером.

### Зависимости

Версии NuGet-пакетов задаются централизованно в `Directory.Packages.props` (Central Package Management). В файлах проектов `PackageReference` указывается без атрибута `Version`; новая зависимость добавляется сначала как `PackageVersion` в общем файле.

### Локальный запуск через Aspire

`src/LtiIntegrationGateway.AppHost` поднимает локальный контур: PostgreSQL в контейнере, сервис управления в двух репликах, по два экземпляра сервиса потоков на интеграцию (`bank-a`, `bank-b`) и dashboard с телеметрией.

```bash
dotnet run --project src/LtiIntegrationGateway.AppHost
```

Требуется запущенный Docker. Ссылку на dashboard AppHost печатает при старте; оба сервиса экспортируют в него traces и metrics по OTLP. В списке ресурсов dashboard показывает состояние готовности: AppHost опрашивает `/health/ready` каждого сервиса (проба включает проверку хранилища), поэтому упавший или неготовый экземпляр виден без перехода в логи. Ссылки ресурсов ведут в Swagger UI (`/swagger`), а не на корень сервиса. Ключ управляющего API для разработки — `dev-management-api-key` (задаётся в AppHost, для эксплуатации не используется).

### Симуляция живого контура

AppHost поднимает рядом со шлюзом два dev-сервиса из `simulation/`: `product` (продукт — участник
шины) и `integration` (внешняя система — HTTP-контракт). Порты фиксированы: управляющий API —
`http://localhost:5080`, продукт — `http://localhost:5081`, внешняя система — `http://localhost:5082`;
канал вызывает внешнюю систему по `https://localhost:5443` (dev-сертификат).

Порядок запуска задан ожиданиями Aspire: `management` (готов) → оба `flow-*` (готовы) → `product` →
`integration`. Скриптов нет: продукт при старте сам регистрирует конфигурацию в управляющем API —
канал `http`, каналы `product-orders-async` и `product-orders-sync` с контрактами из
`simulation/contracts` и маршрут `product`, — ждёт её применения экземплярами интеграции и только
потом начинает отправку. Поэтому готовность продукта (`/health/ready`) означает «конфигурация
зарегистрирована», и внешняя система стартует уже после неё. Оба входящих сценария идут через
`flow-bank-a`.

Дальше контур работает сам, раз в 5 секунд в каждую сторону:

1. **product → flow → integration (outbound).** Продукт публикует `OutboundRequest` `POST /customer`
   с телом `{"name":"customer-N"}`; `flow-bank-a` вызывает `POST /customer` внешней системы;
   `integration` отвечает `{"status":"ok","message":"recieved customer-N"}`; шлюз публикует
   `OutboundResult` в `product.inbox`, продукт пишет ответ в лог.
2. **integration → flow → product (inbound async).** `integration` вызывает `POST /order` шлюза;
   `flow-bank-a` проверяет тело по контракту канала `product-orders-async` и публикует
   `InboundMessage` в `product.inbox`; продукт пишет заказ в лог.
3. **integration → flow → product (inbound sync).** `integration` вызывает `GET /order/{orderid}`;
   `flow-bank-a` публикует `InboundMessage` с `reply_expected = true`; продукт пишет вызов в лог и
   отвечает сгенерированным заказом; шлюз возвращает ответ внешней системе, `integration` пишет его
   в лог.

Все принятые и отправленные сообщения логируются в `product` и `integration` — это и есть экран
прогона. В журналах шлюза видны статусы доставки, коды и тела ответов: `InboundMessageLogs`
(`Sent` для async, `Replied` для sync) и `OutboundMessageLogs`.

Swagger UI: `http://localhost:5081/swagger` (собственное API продукта `/openapi/v1.json` и оба
контракта `/contracts/product-orders-async.json`, `/contracts/product-orders-sync.json`) и
`http://localhost:5082/swagger` (внешняя система: `POST /customer`). Опубликованные входящие контракты
смотрит `flow`: у каждого экземпляра сводный документ `/openapi/inbound.json` и UI `/swagger` (адрес
печатает dashboard). Подробности решений — в `openspec/changes/` (изменение
`2026-11-01-debug-simulation`).

Пароль PostgreSQL для разработки фиксирован (`dev-postgres-password`), данные хранятся в томе
`lti-gateway-postgres-data`. Смотреть записи удобно в pgweb — AppHost поднимает его вместе с базой:
`http://localhost:8081` (подключён к БД `gateway`, пользователь `postgres`). Пароль нельзя менять без
пересоздания тома: PostgreSQL сохраняет пароль первого запуска. Если запуск завершается ошибкой
`28P01: password authentication failed`, удалите том и повторите запуск:

```bash
docker volume rm lti-gateway-postgres-data
```

Старые тома прежних конфигураций (`lti-postgres-data`, `ltiintegrationgateway.apphost-*-postgres-data`)
можно удалить: dev-данные не мигрируются.

AppHost — инструмент разработки. В Kubernetes он не разворачивается: прод-манифесты ведутся отдельно, а `aspire publish` используется только как вспомогательное средство.

## Настройка

### Строка подключения

Приложение не запускается без строки подключения `ConnectionStrings:Gateway`. Для локального запуска нужен PostgreSQL:

```json
{
  "ConnectionStrings": {
    "Gateway": "Host=localhost;Port=5432;Database=gateway_dev;Username=postgres;Password=postgres"
  }
}
```

Значение можно задать в `appsettings.json`, `appsettings.Development.json` или переменной окружения:

```text
ConnectionStrings__Gateway=Host=localhost;Port=5432;Database=gateway_dev;Username=postgres;Password=postgres
```

Если ключ отсутствует или пуст, приложение завершает запуск с ошибкой, содержащей имя ключа. Это ожидаемая проверка конфигурации.

Размер пула соединений по умолчанию — 20; явно заданный в строке подключения `Maximum Pool Size`
не переопределяется. Имя базы данных обязательно.

Схемой владеет только `Management`: он применяет миграции при старте. `Flow` миграции не применяет и при
несовместимой схеме завершает запросы ошибкой. Для эксплуатации достаточно разделить права: роли
`management` нужны `CREATE`/`ALTER` в схеме (миграции), роли `flow` — только `SELECT`/`INSERT`/`UPDATE`
по таблицам. Транспорт Rebus использует общую таблицу `messages`, поэтому ролям обоих сервисов нужны
права на неё. Для локальной базы, созданной на старой dev-схеме, миграция старых данных не
гарантируется: такую базу следует удалить и создать заново.

### Управляющий API

Управляющий API использует ключ из конфигурации `Management:ApiKey`. Для локальной настройки можно задать переменную окружения:

```text
Management__ApiKey=<secret>
```

Ключ передаётся в заголовке `X-Management-Api-Key` (имя заголовка настраивается). Если ключ в конфигурации не задан, управляющий API отвечает `503`; если заголовок отсутствует или содержит неверное значение — `401`. Значения ключей не следует добавлять в репозиторий.

### Наблюдаемость OpenTelemetry

По умолчанию экспорт телеметрии выключен. Для включения задайте параметры:

| Ключ конфигурации | По умолчанию | Назначение |
|---|---:|---|
| `Observability:Otel:Enabled` | `false` | Включает OTLP-экспорт traces и metrics |
| `Observability:Otel:Endpoint` | — | Абсолютный URI `http` или `https`; обязателен при включённой телеметрии |
| `Observability:Otel:ServiceName` | `management` или `flow` | Имя сервиса в OTel resource; `OTEL_SERVICE_NAME` имеет приоритет |
| `Observability:Otel:ServiceVersion` | версия сборки | Версия сервиса в OTel resource |
| `Observability:Otel:SamplingRatio` | `1.0` | Коэффициент сэмплирования от `0` до `1` |
| `Observability:Otel:ExportIntervalSeconds` | `60` | Интервал экспорта метрик, от `1` до `3600` секунд |

Например, через переменные окружения:

```text
Observability__Otel__Enabled=true
Observability__Otel__Endpoint=http://localhost:4317
```

При включённой телеметрии некорректный endpoint или параметр останавливает запуск. Сообщение об ошибке указывает ключ настройки, но не раскрывает её значение.

Приложение экспортирует стандартные ASP.NET Core, `HttpClient` и runtime-метрики, а также бизнес-метрики `lti.gateway.inbound.*`, `lti.gateway.outbound.*`, gauge `lti.gateway.outbound.pending` и метрики применения конфигурации `lti.gateway.config.applied_version` и `lti.gateway.config.lag`. Бизнес-метрики и трассировки `Flow` содержат измерение `integration`; `service.instance.id` различает реплики. Трассируются входящие HTTP-запросы, исходящие операции, обработка сообщений Rebus и доставка сохранённых результатов.

OTel logs, дашборды, алерты и метрики длины очередей промышленного транспорта в текущий объём не входят.

## Сборка, тестирование и запуск

Команды выполняются из корня репозитория.

```bash
# восстановление зависимостей и сборка
 dotnet build LtiIntegrationGateway.slnx

# запуск тестов TUnit через Microsoft.Testing.Platform
 dotnet test LtiIntegrationGateway.slnx

# запуск сервиса управления
 dotnet run --project src/LtiIntegrationGateway.Management

# запуск экземпляра потоков для интеграции bank-a
 dotnet run --project src/LtiIntegrationGateway.Flow -- --Gateway:Integration=bank-a
```

`Flow` не запускается без `Gateway:Integration`: имя интеграции определяет входную очередь
`lti.gateway.<integration>.outbound`, error-queue `lti.gateway.<integration>.error` и область действия
проверок.

## Проверки состояния

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health/live` | Liveness-проба. Возвращает `200` и не обращается к БД, Rebus или внешним системам |
| `GET` | `/health/ready` | Readiness-проба. Проверяет доступность хранилища и возвращает `200` или `503` |

Readiness проверяет только доступность хранилища. Транспорт Rebus — PostgreSQL, поэтому отдельной проверки
внешнего брокера нет.

## Контракты

Исходные контракты находятся в `protos/` в корне репозитория:

- [`v1/integration_messages.proto`](protos/v1/integration_messages.proto) — сообщения Rebus в пакете `lti.gateway.messages.v1`: `OutboundRequest`, `OutboundResult`, `InboundMessage`, `InboundResponse` и связанные типы.
- [`v1/management_api.proto`](protos/v1/management_api.proto) — управляющий API в пакете `lti.gateway.management.v1`.

Файлы `.proto` являются исходным определением контрактов. C#-типы генерируются при сборке через `Grpc.Tools`; сгенерированный код вручную не редактируется и в репозитории не хранится. Отдельный NuGet-пакет контрактов не публикуется: потребители получают `.proto` из репозитория и генерируют типы самостоятельно.

Для сообщений Rebus используется ProtoJSON (UTF-8). Профиль сериализации, включая правила имён полей, представление `bytes` и заголовки Rebus, документирован в самих `.proto` и обязателен для потребителей. Обязательные поля `OutboundRequest` дополнительно проверяются `MessageContractValidator`.

При изменении опубликованных контрактов необходимо соблюдать правила совместимости Protobuf и обновлять документацию по требованиям из [`AGENTS.md`](AGENTS.md).

## Обмен сообщениями Rebus

Текущие имена очередей:

| Очередь | Назначение |
|---|---|
| `lti.gateway.<integration>.outbound` | Входящие для интеграции `OutboundRequest` |
| `lti.gateway.<integration>.error` | Сообщения интеграции, которые не удалось обработать после исчерпания попыток Rebus |
| `<product_id>.inbox` | Очередь соответствующего продукта; адрес вычисляется из `product_id` |

Для синхронного режима каждый экземпляр дополнительно читает собственную reply-очередь
`lti.gateway.<integration>.reply.<instance_id>`: ответ продукта адресуется ей заголовком
`rbs2-return-address`, поэтому при нескольких репликах его получает экземпляр, принявший вызов.

Адрес зависит от интеграции, а не от числа реплик: продукт отправляет сообщение в очередь интеграции,
а реплики конкурируют за её сообщения. Имя интеграции должно соответствовать
`^[a-z][a-z0-9-]{1,31}$`; адрес с другим именем отклоняется. Очередь продукта не задаётся произвольным
адресом: для `product_id = dpv` используется `dpv.inbox`.

Транспорт Rebus — PostgreSQL: очередь является записью в общей таблице `messages`, сообщения переживают
перезапуск процесса. Шина рассматривается как доверенная зона: все участники имеют доступ к таблице,
изоляция интеграций обеспечивается конфигурацией и раздельными ingress.

## Каналы и интеграционные контуры

### Исходящий контур

Продукт публикует `OutboundRequest` в `lti.gateway.<integration>.outbound`. Сообщение содержит идентификатор продукта, имя канала, HTTP-метод, относительный путь, тело и необходимые метаданные. Шлюз проверяет сообщение, принадлежность канала продукту и интеграции, загружает активную ревизию канала, выполняет HTTP-вызов и отправляет `OutboundResult` в вычисленную очередь продукта.

Маршруты продуктов, каналы и операции принадлежат интеграции: одинаковые имена в разных интеграциях не
конфликтуют, а канал другой интеграции отклоняется с `CHANNEL_NOT_ALLOWED`. Одинаковый `message_id` в
другой интеграции — независимая операция.

Повторная обработка сообщения с тем же `message_id` не должна повторно вызывать внешнюю систему: завершённый результат восстанавливается из сохранённой операции и журнала. Результат сначала сохраняется в БД со статусом доставки `Pending`, после чего отправляется продукту. Фоновый `OutboundResultDispatcher` повторяет доставку недоставленных результатов своей интеграции.

Гарантия доставки результата — «минимум один раз». В отдельных сбойных ситуациях возможна повторная отправка, поэтому продукт должен выполнять дедупликацию по `message_id`.

### Входящий контур

Входящие HTTP endpoint-ы формируются из опубликованных OpenAPI-контрактов. При публикации контракта шлюз проверяет документ и конфликты маршрутов внутри интеграции. Активация фиксирует желаемое состояние; экземпляры `Flow` применяют его без перезапуска не позднее 5 секунд (период сверки — 2 секунды). Маршруты другой интеграции в экземпляре не регистрируются.

При вызове endpoint шлюз проверяет параметры, Content-Type, аутентификацию и тело запроса по схеме OpenAPI. После успешной проверки он передаёт `InboundMessage` в очередь продукта. Режим ответа входящего канала может быть асинхронным (`ASYNC`) или синхронным (`SYNC`); подробные правила обработки, статусы и коды ошибок описаны в OpenSpec Specs.

Текущая поддержка входящих документов: OpenAPI 3.0; Swagger 2.0 конвертируется при загрузке; OpenAPI 3.1 не поддерживается. Разрешены локальные `$ref`; внешние ссылки запрещены. Архитектурные ограничения и фактический механизм маршрутизации описаны в [`ARCHITECTURE.md`](ARCHITECTURE.md), требования к поведению — в `openspec/specs/`.

### Управляющий API

Управляющий API предоставляет операции для работы с исходящими и входящими каналами, ревизиями, маршрутами продуктов, OpenAPI-контрактами, настройками операций и состоянием интеграций. Он описан в [`management_api.proto`](protos/v1/management_api.proto) и доступен через gRPC и REST посредством JSON transcoding.

Тот же контракт опубликован как OpenAPI-документ: `/openapi/management.json`, интерактивная документация —
`/swagger`. Документ строится сервисом `Management` при старте из дескриптора `management_api.proto`
(пути — из аннотаций `google.api.http`, схемы и описания — из сообщений и комментариев), поэтому
совпадает с gRPC-контрактом. Оба адреса не требуют ключа API, но сами управляющие вызовы из Swagger UI
требуют его указать (кнопка Authorize).

Полный контракт методов, путей, полей и ответов следует смотреть в `.proto`. Функциональные требования и сценарии управления — в соответствующих OpenSpec Specs.

## Миграции базы данных

Миграции EF Core находятся в `src/LtiIntegrationGateway.Core/Infrastructure/Persistence/Migrations` и
применяются при старте только сервисом `Management`. `Flow` их не применяет.

Создание миграции:

```bash
 dotnet ef migrations add <Name> \
   --project src/LtiIntegrationGateway.Core \
   --startup-project src/LtiIntegrationGateway.Core \
   --output-dir Infrastructure/Persistence/Migrations
```

Конфигурация использует PostgreSQL; миграции создаются под провайдер Npgsql. При промышленной
эксплуатации применяйте их отдельным шагом выката (порядок ArgoCD: management → flow) и следите за
expand/contract-совместимостью: новые колонки и таблицы добавляются до перевода чтения, удаление —
в следующем релизе.

## Текущие ограничения и подготовка к эксплуатации

Текущая реализация содержит начальные инфраструктурные решения, которые не следует считать готовой промышленной конфигурацией:

- Rebus использует транспорт PostgreSQL: очередь — это запись в общей таблице `messages`, сообщения переживают перезапуск процесса.
- Хранилищем служит PostgreSQL; миграции применяет при старте только `Management`.
- Распределённых блокировок нет: конкурентная выборка недоставленных результатов выполняется через `FOR UPDATE SKIP LOCKED`, а уникальность активной конфигурации обеспечивают частичные уникальные индексы.
- Ограничение частоты входящих запросов действует в пределах экземпляра: суммарный бюджет интеграции равен сумме бюджетов реплик. Распределённый лимитер не реализован.
- Изоляция интеграций конфигурационная и сетевая на уровне ingress; egress-политики и egress-прокси не реализованы. Секреты общие для management и flow, поэтому любой экземпляр flow располагает ключами всех интеграций.
- Секреты читаются через конфигурацию приложения; промышленный secret provider не выбран.
- Для управляющего API используется API key; интеграция с корпоративным IdP и ролевая модель не реализованы.
- OAuth2 client credentials для исходящих каналов не реализован.

Перед промышленной эксплуатацией необходимо закрыть эти вопросы и проверить целевые требования по безопасности, надёжности, масштабированию, наблюдаемости и инфраструктуре. Актуальный перечень открытых системных вопросов и подробные ограничения ведутся в архитектурной документации и OpenSpec.
